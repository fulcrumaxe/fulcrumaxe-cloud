## Tenancy and RLS

Every tenant-scoped table carries `account_id` and has row-level security both enabled and forced, keyed against the `app.account_id` Postgres session setting that `packages/db/src/withTenant.ts` sets with `SET LOCAL` for the lifetime of one transaction. A connection with no tenant context set matches no rows in any policy, so the default is deny, not allow. See [the data model's RLS conventions](data-model.md#rls-conventions) for the composite-foreign-key and column-grant details, and [`packages/db`](packages/db.md) for the package itself.

`withTenant` is the one door to a tenant table: it sets `app.account_id` (and `app.user_id`, `app.token_id` when given) for one transaction with a parameterized `set_config`, so the setting can't outlive the transaction on a pooled connection. Where a write must do more than a tenant member's grant allows, the table has no `INSERT` or `UPDATE` grant for `app_user` at all and a `SECURITY DEFINER` function does the write, checking the caller's own role and state inside (the assistant's cost tables below are an example). `packages/db/src/rlsInventory.ts` fails the test run if a `public` table has RLS missing or not forced.

## Roles and grants

`packages/db/migrations/0001_core.sql` creates `app_user` and `platform_ops`; `packages/db/migrations/0200_partners.sql` creates `partner_user`. These three are created `LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS` — none of them can create databases, create other roles, or bypass RLS on their own. Later migrations add a few more login roles (such as `ops_console` and `exposure_writer`) and many `NOLOGIN` roles (such as `agent_run_writer` and `work_item_approval_definer`) that exist only to own one `SECURITY DEFINER` function or one narrow write path; none of them has `BYPASSRLS` either. `app_user` is the tenant-facing role and only ever sees rows its RLS policies admit; `platform_ops` carries the platform's own broader read/write grants (and, on several tables, a `platform_ops_full_access`/`platform_ops_read_access` policy in addition to its grants); `partner_user` is scoped the same way as `app_user` but against `app.partner_id` rather than `app.account_id`. Several grants are column-level rather than table-wide — see [the data model](data-model.md#rls-conventions) for examples.

## `audit_log`

`app_user` has no `INSERT` grant on `audit_log` at all; the only way it can produce a row is `audit_write()`, a `SECURITY DEFINER` function owned by `platform_ops` (`packages/db/migrations/0008_audit_log_append_only.sql`, `#91`). The function stamps `account_id` and `actor` from the caller's own verified session state rather than trusting any caller-supplied value, checks `action` against a literal allowlist, and overwrites a caller-supplied `actor` key inside the payload instead of trusting it. See [the data model](data-model.md#append-only-evidence-tables) for the companion `audit_write_system` function and the `ledger` table's append-only-by-grant equivalent.

## CSRF

`apps/web/lib/shell/csrf.ts`'s `evaluateCsrf` classifies every `/api/*` request by which credentials it carries before anything else runs: `csrfStep` is the first entry in `apps/web/middleware.ts`'s `STEPS` array. A request carrying the session cookie and no `Authorization` header must, for any mutating method, either declare `Sec-Fetch-Site: same-origin` or send an `Origin` matching the configured workspace origin (`FX_APP_ORIGIN`), and must send `Content-Type: application/json` (the `/api/csp-report` route is the one path exempted from the content-type half of that check, since it accepts a browser's own CSP report body, but not from the origin check). A request carrying both a cookie and an `Authorization` header is rejected outright on `/api/v1/*` or any mutation, since the two credentials disagree about which the request is asserting. A bearer token with no cookie is accepted only on `/api/v1/*` and is otherwise left to the route's own authenticator. `apps/web/middleware.ts` also unconditionally deletes any client-sent `x-fx-user-id`/`x-fx-account-id`/`x-fx-token-id`/`x-fx-scopes`/`x-fx-principal-*` header before running any step, so a caller cannot forge a principal header that a later step would otherwise trust.

## Sessions

Sessions are signed JWTs (`packages/core/src/auth/session.ts`, via `jose`) stored in a cookie named `__Host-fx_session` — the `__Host-` prefix requires the cookie to also be `Secure`, `Path=/`, and carry no `Domain`, so the browser refuses to set it under any weaker combination. Sessions carry a default 24-hour idle limit and 30-day absolute limit, both env-configurable. `apps/web/middleware.ts`'s `sessionStep` verifies the cookie and exposes `x-fx-user-id`/`x-fx-account-id` headers to downstream code, but it runs on the Edge runtime with no database connection, so it cannot re-check revocation. `0604_session_epoch.sql` adds `users.session_epoch`, embedded in every signed session at sign-in; `apps/web/lib/shell/session-guard.ts`'s `resolveActiveSession` is the one place a Node-runtime handler both verifies the cookie and re-checks its embedded epoch against the live `users.session_epoch` value, so a "sign out everywhere" action (`packages/core/src/auth/identity.ts`'s `bumpSessionEpoch`) revokes a session even though its JWT signature and expiry are still valid. Only handlers that call `resolveActiveSession` (not `verifySession` directly) honour that revocation.

## Workspace subscription gate

Workspace licence activation: the fulcrumaxe-os licence-activation module (`/api/license/*`, `apps/activation/**`) is not part of cloud, and is not shipped. `apps/workspace/profiles/cloud.json`'s `app_modules` no longer lists `activation`, so `apps/workspace/build/profile.mjs`'s filter drops every `apps/activation/*` tag from the built `index.html`; `apps/workspace/import/checks.mjs --ship` (via `apps/workspace/import/rules.mjs`'s `ACTIVATION_PATH_RE`/`checkShipNoLicenseActivation`/`checkShipNoSubscriptionBypass`) additionally fails the build if a `dist/` path under `apps/activation/`, any of `FULCLicense`/`/api/license/`/"Activate license"/"license key", or a subscription-gate bypass flag survives in shipped bytes. The source files stay in the imported fork tree (`apps/workspace/import/allowlist.txt`'s `apps/activation/**` entry is unchanged) but are never reachable. `apps/web/lib/shell/shell-paths.ts` no longer maps `/api/license/status` to anything, so a request to it now 404s the same way any unmapped path does.

A subscription's activation unlocks the workspace instead. `apps/web/lib/shell/session-routes.ts`'s `meResponse` adds one field, `workspace_access`, to `auth/me`/`profile`, derived from the account-status model (`accounts.status`, `packages/billing/src/accountStatus.ts`) through billing's own authorized `readAccountStatus(ctx, input)` read (never a raw query against `accounts` from this route): `active`/`past_due`/`paused`/`model_key_broken` map to `open`; `unsubscribed` maps to `no_subscription`; `cancelled` maps to `subscription_ended`; any other value, or no readable row, fails closed to `no_subscription`. The field carries no plan, price, Stripe id or raw status string. `apps/workspace/shell/core/boot.js` calls `apps/workspace/shell/core/subscription-gate.js`'s `render()` instead of `window.showDesktop()` whenever `workspace_access !== "open"`, showing a full-window screen with no desktop, desktop icons, dock, taskbar, tray or app window, and issuing no `/api/entitlements/me` or `/api/v1/*` request.

This gate is cosmetic by design, not the access control: the spend package's `reserve()` (`packages/spend/src/reserve.ts`) already denies a run server-side for any account whose derived status is not `active` (or `past_due` within its 7-day grace window), independent of anything the client renders. A client that forced `workspace_access: "open"` locally would reach only an empty desktop whose own server calls are still decided server-side.

## Security headers and CSP reporting

`apps/web/lib/shell/headers.ts`'s `SHELL_SECURITY_HEADERS` list (Content-Security-Policy, a `Reporting-Endpoints` header pointing at `/api/csp-report`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Cross-Origin-Opener-Policy: same-origin`, and a restrictive `Permissions-Policy`) is applied two ways: `apps/web/next.config.mjs`'s `headers()` function serves it on `/`, on `/api` and on every `/api/` path except a site's preview render path (with its own literal copy of the same values, since `next.config.mjs` cannot `import` a TypeScript module; the render path exception is below), and `apps/web/lib/shell/headers.ts`'s `applySecurityHeaders` helper is called directly by individual route handlers such as `apps/web/app/api/csp-report/route.ts`. The CSP's `frame-src` is `'self'`, because the one page the shell frames is a site's preview render at `/api/v1/sites/<id>/preview/render`; that path is served with its own response policy and without the shell's CSP, whose `frame-ancestors 'none'` would refuse the frame, and it keeps every other shell header (`apps/web/next.config.mjs`, #929). Next matches header sources case-insensitively, so `apps/web/middleware.ts`'s `renderPathCaseStep` answers any other-case spelling of that path with a 404 that carries the shell headers. `/s/:path*` — the content-hashed static-asset prefix introduced in `#172` — instead gets `SHELL_STATIC_ASSET_HEADERS`: the same `SHELL_SECURITY_HEADERS` list plus `Cache-Control: public, max-age=31536000, immutable`, safe because every file under that prefix is named by a hash of its own build contents, so a changed byte always produces a new path rather than reusing a cached one. The CSP's `default-src 'none'` denies everything not explicitly listed; `report-to csp` plus the `Reporting-Endpoints` header sends violations to `/api/csp-report`, which accepts only `application/csp-report` or `application/reports+json`, enforces a 16 KB body limit against actual bytes read (not a trusted `Content-Length`), logs one structured line, and stores nothing in any table.

`require-trusted-types-for 'script'` and `trusted-types 'none'` are enforced directives inside that same `Content-Security-Policy` value, not a separate `Content-Security-Policy-Report-Only` header (removed once a live walk, driven through every reachable workspace-shell surface, recorded zero violations under Report-Only first) -- `trusted-types 'none'` blocks any script from creating a Trusted Types policy at all, since the shell needs none. `apps/workspace/import/rules.mjs`'s `TRUSTED_TYPES_SINK_RE` is a best-effort, pre-browser lint that catches ordinary sink spellings in CI; it is not the security control and is not extended to chase further evasions (indirect eval, computed/concatenated keys, and similar), because enforced Trusted Types blocks every one of those at runtime regardless of source spelling.

## The trust gate

`packages/trust/src/author-trust.ts`'s `classifyAuthor` decides whether a GitHub comment/event author is trusted using only their GitHub-authenticated login and their real repo permission (`admin`/`maintain`/`write` when a customer opts in, or an explicit allowlist) — its input type carries no body field at all, so no text in a comment can influence the classification, structurally rather than by convention. `packages/trust/src/work-gate.ts`'s `canCreateWork` turns that classification into whether an event may create work at all; `storeWorkEvent` re-derives the same classification and returns it alongside a `rawBody` (byte-identical to what the author wrote, for display) and a `storedBody` (untouched for a trusted author, sanitized and fenced for anyone else) — the file's own comment states the rule a caller must follow: display `rawBody`, but never build a model prompt from anything but `storedBody`.

## The merge gate's trust rules

Every merge the product makes passes `runMergeGate` (`packages/pipeline/src/build/mergeGate.ts`). `packages/pipeline/test/build/mergeCallSites.test.ts` reads the production sources and fails when a file outside a short, reviewed list can call the merge, the queue enqueue, the auto-merge document or the merge endpoint, or mint the credential a merge uses. A new caller has to be added to that list in a change a reviewer reads.

- **Who may have a pull request merged.** `packages/pipeline/src/build/authorTrust.ts` decides from identity only, in this order: the platform's own App bot accounts, then the intake allowlist, then `admin` or `maintain` on the repository, read live from GitHub on each run and never stored. `write` does not count. A missing login is untrusted; a read that fails, times out or names no permission is `unverified`, and the gate stops (`pr_author_unverified`) and asks again next run. An untrusted author stops it with `pr_author_untrusted`. This applies to the public pull request of a paired item whatever the repository says about itself, and to any pull request in a public repository.
- **`fx-gate1` counts only from our App.** For a cloud item the gate reads who posted the newest `fx-gate1` status on the head (`packages/pipeline/src/review/gate1Creator.ts`). It counts only when the poster is our GitHub App's bot account (type `Bot`, login compared exactly). A status posted by a person, a token or another app reads as failed and stops the gate with `gate1_status_foreign`. The read uses GitHub's own record of the poster; no text a pull request controls is read.
- **Reviews on the exact head.** A reviewer's verdict counts only for the head sha it reviewed, and a run on a customer's runner counts only when local review is on and that runner is trusted for the role.
- **CI on the head.** `runMergeGate` stops with `ci_not_green` unless CI on the exact head is green and every signal the item expects is present. When CI is entirely green and the repository has CI of its own (not only the cloud's review status), an acceptance tester whose latest run succeeded with the verdict `unverifiable` counts as covered; every other non-pass verdict still stops the gate. A repository whose own CI is still running is not also given `repo_ci_missing`, which only a person could fix.
- **Ordering.** A direct merge takes a per-repository lease that excludes the merge queue's slot, so the order check guarding the queue also guards the direct merge.
- **Queue jump stays on the cloud's own gate.** Asking GitHub for the front of the merge queue is reachable only from the gate that merges pull requests the platform built, only for a repository listed in `FX_GATE1_ATTEST_REPOS`, only while `FX_QUEUE_JUMP` is unset, empty or `on` (any other value, `off` included, reads as off), and at most once per repository per `FX_QUEUE_JUMP_MIN_MINUTES` (`packages/pipeline/src/review/queueJump.ts`, #944). The jump uses a GraphQL document pinned beside the others in `packages/github/src/mergeGateGraphql.ts`; GitHub refusing it never skips the queue's rules, because the same pull request is enqueued once more as a plain entry (`packages/pipeline/src/build/githubMergePort.ts`).

## `gh-policy`

`packages/gh-policy/src/decide.ts`'s `decide` is a pure policy function with no network, filesystem or process access (`packages/gh-policy/src/types.ts`'s file header) — it only approves or denies a `ProxyRequest` based on the fields it is handed (method, host, path, and pre-extracted `gitRefUpdates`/`labelNames`/`patchFields`), scoping the resulting token to specific repositories and permissions rather than handing out a broad credential. Its own type-level documentation is explicit that it trusts its caller (the proxy) to derive those three fields from the exact parsed body of the same request being decided, and to forward that body byte-identical to what was parsed — `decide()` itself has no way to verify either.

## The sandbox network policy

`packages/runner/src/networkPolicy.ts`'s `networkPolicy` computes a deny-by-default list of allowed destinations for an agent run: the tenant's model endpoint (`ai-gateway.vercel.sh` or `api.anthropic.com`, matched to the connection's provider), GitHub hosts reached only through this repo's own proxy (never `github.com`/`api.github.com` directly), and, only during the dependency-install phase, `registry.npmjs.org` and `npm.pkg.github.com`. The module never returns a wildcard rule, so any caller that denies everything not on the returned list is, by construction, deny-by-default — enforcing that a caller actually does so is a different layer's job: `packages/runner/src/vercelSandboxPort.ts` passes the computed policy to the sandbox when it creates it (and applies it again when a stopped sandbox wakes), and refuses to create a sandbox without one (`SandboxPolicyRequiredError`), because the platform's default for a sandbox is allow-all.

The GitHub proxy's forward host itself is now operator-configured rather than accepted from any syntactically-valid hostname: `packages/runner/src/githubForwardConfig.ts`'s `loadGithubForwardConfig` reads `FX_GH_FORWARD_SUFFIX`/`FX_GH_FORWARD_HOST` and accepts a host only if it is the configured suffix or a subdomain of it, on top of the pre-existing strict-hostname and reserved-name checks. `packages/runner/src/firewallPolicy.ts`'s `buildFirewallPolicy` resolves that host through `packages/net-guard/src`'s `resolveChecked` on every call (never cached) and refuses to build a policy — before ever decrypting the tenant's model key — if the DNS lookup fails or any resolved address is blocked (`isBlockedAddress`: loopback, private, link-local, metadata, multicast or reserved, including an IPv4 address hidden inside an IPv6 literal). This closes an SSRF gap the forward host previously had: an operator-controlled hostname that later re-resolved to an internal address would have been let through the old syntax-only check.

## Verdict envelopes

A reviewer's verdict is a JSON block between `AGENT_OUTPUT` markers at the end of its final message, and the text a reviewer reads (a diff, a log, a pull request body) can contain a block planted to look like a pass. `packages/runner-protocol/src/envelope.ts` therefore takes the last block, never the first. If the last block is malformed there is no verdict, and an earlier block is never used as a fallback. A block body may not contain another opening marker, so an unterminated earlier block can't swallow the real one, and input over 256 KB is refused. On a hosted sandbox, `packages/runner/src/vercelSandboxPort.ts` keeps a fallback for a run whose last turn spoke after the verdict: it is the block of the last main-thread message that carried a marker, only if that message ends with the block (`endsWithEnvelopeBlock`, so a block quoted in the middle of a message with prose after it never counts), it parsed, and it is not a checkpoint. Subagent output, user and tool lines and failed runs never feed it, and a later marker that does not parse clears it. The check is on how the message ends, not on who wrote the block: a quoted block that is the very last thing in a message would still be taken.

## Post-merge verify

The post-merge verify stage drives a real browser at a deployed app, so its inputs are treated as data (`packages/worker/src/verifyRun.ts`, `packages/pipeline/src/verify/envelope.ts`):

- The pipeline decides; nothing a page or a model wrote reaches a prompt, a label or a decision. The tester's answer is strict JSON: any unknown key at any depth rejects the whole envelope, and what a page showed is cut, stripped of control characters and links, and stored as text only.
- A `pass` needs evidence (a step stating what was done and the page fact that showed it, an undo check and, unless the journey is view-only (a filter, sort or reading), a reload); a pass without it ends the row `unverified`, never `verified`.
- The deploy order the cloud places can only say "deploy this commit of this repository": the table has no column for a command, a path, a URL or a credential, and the command lives in the runner's own local configuration (`packages/db/migrations/1004_runner_browser_capabilities.sql`).
- When the repository names a test account, the signed-in account is judged from what the trusted verify server recorded (`signed_in_as`), never from anything the model said (`packages/pipeline/src/verify/rules.ts`); a mismatch, or a method with no trusted record, ends the row `unverified`.
- A saved sign-in that the app has stopped honouring does not end a row as the wrong account. The runner's verify server, not the model, writes a `signed_in_as_unavailable` marker (the single word `sign_in_expired`) when the app's identity route gave no account; the pipeline rejects the marker if it comes beside a `signed_in_as`, and otherwise parks the row (`packages/pipeline/src/verify/envelope.ts`, `packages/pipeline/src/verify/rules.ts`, `packages/fx-runner/src/verifyBrowser/server.ts`, #947). A parked row waits at most 24 hours and at most three parks before it ends `unverified: sign_in_expired` (`packages/worker/src/verifyRun.ts`). A runner reports only a closed state word for its saved sign-in, never the sign-in itself (`packages/core/src/verify/signIn.ts`).
- Only an owner or admin of the account can turn the stage on or change its settings, enforced by the table's policy.

## The assistant's boundaries

`POST /api/v1/assistant/messages` is a chat that reads a repository's work and can propose, never act. What holds it there:

- It accepts a session only; no API token of any kind. The delegation token a runner uses for the assistant's read proxy (`packages/api/src/routes/assistant.ts`) is separate: at most an hour, one repository, scopes `read` and `corrections:write`, revocable like any token, and its power is its creator's current role.
- The model can call only the tools in the closed registry in `packages/core/src/assistant/tools.ts`. A name outside it is dropped. The tools read in-process under the caller's own principal, an item from another repository answers "not found", and the single write, `draft_correction`, creates a `proposed` correction that a person must accept; its optional `add_files` list is checked as a list of at most 10 strings of at most 512 characters, and the tool validates the paths themselves (#978).
- Everything a tool returns is data: repository, issue and GitHub text is defanged and fenced as untrusted, and the fixed system prompt tells the model not to follow instructions in it.
- Money is bounded per conversation. `assistant_conversations` holds the cap fixed at the start, what is spent and what is held for turns in flight; `app_user` can read and insert conversations but only two `SECURITY DEFINER` functions move the money, and `app_user` has no access to the per-turn holds table. A turn is admitted only when spent plus held plus its worst case fits under the cap, so two turns racing at the cap can't both pass. A hold never settled is released after 20 minutes.
- No message text is stored anywhere: the client sends the turns each time, and the tables hold only ids and amounts.
- The device-link table (`assistant_link_codes`) is reachable by `platform_ops` only.

## The operator subscription exception

A customer's Claude subscription credential is never allowed on our hosted sandboxes. The one exception is our own: runs and previews started by an account on the operator allow-list may use our own Claude subscription. `packages/runtime/src/operatorSubscription.ts` is the one place that decides it, from three settings that must all hold (`FX_OPERATOR_SUBSCRIPTION` exactly `on`, the account on `FX_OPERATOR_ACCOUNT_IDS`, a token-shaped `FX_OPERATOR_CLAUDE_OAUTH_TOKEN`); a run needs both its own account and its payer on the list. The token is read only by the worker, when it builds the firewall policy (`buildOperatorFirewallPolicy`), and rides the `api.anthropic.com` rule as a non-enumerable `Authorization` value, like a tenant key. The sandbox's CLI holds the fixed placeholder `brokered-at-firewall` in `CLAUDE_CODE_OAUTH_TOKEN` (so it sends its own OAuth headers) and no `ANTHROPIC_AUTH_TOKEN`. `packages/runtime/src/production/guard.ts` allows exactly that placeholder, only for a spec flagged `operatorSubscription` toward the Anthropic default, and lets the orchestrator env hold the token under its one name only. Usage is recorded under the ledger source `operator_subscription` at $0; the per-run cap still stops a runaway.

## Bring-your-own-key encryption

`packages/model-connection/src/crypto.ts` envelope-encrypts each stored model credential: a fresh random 32-byte data key (DEK) encrypts the plaintext with AES-256-GCM, and a platform key-encryption-key (KEK) wraps the DEK, also under AES-256-GCM, both layers bound to the same additional-authenticated-data (AAD) so decrypting a row's ciphertext under a different AAD (for example, another row's or another account's) fails GCM authentication and throws. `packages/model-connection/src/kek.ts`'s `envKekSource` reads the KEK from `FX_KEK_V{version}` environment variables (32 bytes, base64), versioned so the platform can rotate its root key — `model_connections.kek_version` records which version wrapped a given row's DEK.

## The zero-model-token test rule

`packages/test-guard/src/guard.ts`'s `installModelCallGuard`, wired in via `packages/test-guard/src/setup.ts`, activates only when `FX_FORBID_MODEL_CALLS=1` is set. Active, it patches `fetch` to throw a `ModelCallBlockedError` on any request to `ai-gateway.vercel.sh` or `api.anthropic.com`, and patches `child_process` spawn functions to catch any command invoking the `claude` binary. `.github/workflows/ci.yml` sets `FX_FORBID_MODEL_CALLS: "1"` at the job level, and `scripts/check.sh`'s test step additionally unsets `ANTHROPIC_API_KEY`/`ANTHROPIC_AUTH_TOKEN`/`CLAUDE_CODE_OAUTH_TOKEN` before running `pnpm test` — so the ordinary test run has neither a live credential nor a permitted path to spend one.

## Engine bridge

The engine bridge lets an owner or admin send a small, closed set of commands to the engine running on their own machine, and lets that engine ask the cloud before it spawns an agent or merges. These are the trust rules as merged; the runner side lives in `packages/fx-runner`.

- **Commands are signed.** `packages/runner-protocol/src/engineCommands.ts`'s `signEngineCommand` signs the canonical JSON of a command with the job-signing key, and `verifyEngineCommand` checks it against the runner's keyring. The signed body names one runner (`runner_id`), one repo (`repo_gh_id`), a sequence number and the halt epoch the command was issued under, and carries a fixed `purpose` (`engine_command_v1`) so a signature made over a job can never verify as a command. The worker hands the pull route its signer from `packages/worker/src/compositionRoot.ts`'s `engineCommandSigner`, which is null when the job-signing key is not configured. With no signer, `pullEngineCommands` in `packages/runner-cloud/src/engineCommands.ts` answers 503 `not_configured` and delivers nothing.
- **Kinds and lifetime.** There are seven kinds (`ENGINE_COMMAND_KINDS`): `start_day`, `pause_loop`, `resume_loop`, `answer_ask`, `set_dial`, `request_spawn` and `stop_agent`. Their arguments are a closed shape, checked in the protocol schema and again in the database by `engine_command_args_ok` and a CHECK constraint in `packages/db/migrations/1029_engine_commands.sql`. `set_dial` can reach only eight dial classes, and `request_spawn` only eleven named roles. A command lives at most 600 seconds (`ENGINE_COMMAND_MAX_LIFE_S`, and the `engine_commands_life` constraint), and the verifier refuses one issued more than 60 seconds ahead of its own clock (`MAX_CLOCK_SKEW_S`). A runner refuses a wrong runner, a wrong repo, a sequence number at or below the last it applied, and an expired command (`packages/fx-runner/src/engineBridge/commands.ts`'s `judge`). At most 20 commands wait per runner and repo (`MAX_PENDING_PER_TARGET` in `packages/db/src/engineCommands.ts`).
- **Session-only issue.** The issue route (`packages/api/src/routes/engine-commands.ts`) is owner or admin and session only: it names no `principals`, so an API token is refused with 403 `session_required`. The insert policy in migration 1029 checks the same thing in the database: the issuer is the session's own user, holds the `owner` or `admin` role, and the session is not a runner's. The runner's pull moves only its own rows from pending to delivered, then acks once; a person can only cancel one that is still pending.
- **The halt marker.** Migration `packages/db/migrations/1031_engine_halt.sql` adds one row per repo in `engine_repo_controls`: `halted_at`, and a `halt_epoch` that goes up by one on each halt and is never lowered or changed by a clear. A BEFORE INSERT trigger on `engine_commands` refuses `start_day`, `resume_loop`, `request_spawn` and `set_dial` while the repo is halted, by raising SQLSTATE `HX409` (`engine_halted`). `pause_loop`, `answer_ask` and `stop_agent` stay allowed. The trigger also stamps the current epoch into `halt_epoch_at_issue`. The same trigger on `engine_decisions` refuses every decide, and the decide route answers `ask` with `halted: true` and no receipt while the repo is halted, replays included, using its own `HALTED_REPLY` constant in `packages/runner-cloud/src/engineDecide.ts`. The pull route also withholds a halted repo's start-like commands, and any start-like command issued under an earlier epoch than the current one, so clearing a halt starts nothing by itself. The engine repos list reads the marker back as `halted`, `halted_at`, `halted_by` and `halt_epoch`, plus a derived `halt_pending` that stays true until the runner has reported applying the current epoch (`packages/api/src/routes/engine.ts`, `packages/core/src/engine/panels.ts`). While operate is off for the account, no command is delivered at all.
- **Who can set or clear a halt.** The marker is written only by two `SECURITY DEFINER` functions, `engine_halt_set` and `engine_halt_clear`, owned by `engine_halt_definer`, a `NOLOGIN` role with no other privileged attribute (the migration raises if it has one). Both call `engine_halt_assert_person`, which refuses a `platform_ops` login and any runner session, and then requires a verified `owner` or `admin` member of an active account. `app_user` has `SELECT` on the marker and nothing more. The routes in `packages/api/src/routes/engine-halt.ts` are session only on top of that. `engine_halt_set` also records who halted, in `halted_by` (`packages/db/migrations/1038_engine_halt_by.sql`, #1046), taken from the session's own user id and never from an argument. The repos list shows that person's name only when they are a member of the repo's own account, so a stale or foreign id names nobody (`packages/core/src/engine/panels.ts`).
- **Tenant isolation.** `engine_commands`, `engine_decisions`, `engine_decision_answers` and `engine_repo_controls` all have row-level security enabled and forced, keyed on `app.account_id`. The runner routes also filter by account in their own SQL: the pull selects covered repos with `rn.account_id = $2` and the runner id from the verified key (`packages/runner-cloud/src/engineCommands.ts`), and `findEngineTarget` in `packages/db/src/engineCommands.ts` filters on both `account_id` and the repo. The halt helpers refuse when the account they are given is not the session's.
- **Decisions are written by a verified runner.** Only a session that sets `app.runner_id` for a live runner of the account can insert an `engine_decisions` row, and only an owner or admin, in their own name and outside a runner session, can write an answer (`packages/db/migrations/1030_engine_decisions.sql`). A decide route with no audit writer answers 503 before reading or writing anything (`packages/runner-cloud/src/engineDecide.ts`).
- **The runner's decide socket.** `packages/fx-runner/src/engineBridge/decideSocket.ts` serves the engine hook on a unix socket set to mode 0600, inside a 0700 directory that must belong to the runner's user and not be a link. A repo the runner is not paired with is refused locally (`wrong_repo`), as is one whose last pull said operate is off. The daemon wires the check as `puller.operateEnabled(id) === true` (`packages/fx-runner/src/engineBridge/daemon.ts`), so until a pull has said operate is on, the socket refuses.
- **The ceiling file.** `packages/fx-runner/src/engineBridge/ceiling.ts` writes a file the engine reads, mapping `ask` to ceiling 1 and `announce` or `act` to 5, for `agent.spawn` and both merge classes (`merge.standard`, `merge.fast-path`). A halted repo gets 1 for all three. The file is written 0600 through a temp file and rename, and lives 900 seconds. A failed fetch leaves the old file in place, and, as the file's own header comment states, once it runs out the engine reads ceiling 1 for all three classes. The runner never writes a looser file from a stale or unreadable answer.
- **The runner kill path (#995).** When a pull reports a higher `halt_epoch`, or a person runs `fx-runner engine-host stop` on the machine, `packages/fx-runner/src/engineBridge/halt.ts` writes `engine-halt.json` first, atomically and without following a link, then signals the host's process group (SIGTERM, then SIGKILL after 10 seconds). On Linux it also kills the host's systemd user scope and reads its `cgroup.procs` until empty. The result carries a `method` (`scope`, `group_only` or `none`) and a survivor count, and unknown counts as alive. A local stop is marked `local_stop` in the file, which a cloud control cannot clear, and a clear rewrites the file to not halted without restarting the host.
- **The hosted Team Lead (#997, #1009, #1011).** `fx-runner engine-host start` runs the engine's Team Lead as one headless `claude` under a supervisor (`packages/fx-runner/src/engineHost/supervisor.ts`). It refuses to start unless the bridge is enabled for the repo, the cloud's operate switch is on, no halt file says halted, a systemd user scope can be used to prove a kill, the process is not root, and no other host is running (`packages/fx-runner/src/commands/engineHost.ts`'s `REFUSALS`). The host's arguments are fixed, plus `--resume <uuid>` after a crash; `assertHostArgv` refuses any extra flag and any argument naming permissions, settings, allowed tools or MCP config. Its environment is six variables (`PATH`, `HOME`, `XDG_RUNTIME_DIR`, `DBUS_SESSION_BUS_ADDRESS`, `AUTONOMOUS_TEAM_STATE_DIR`, `LANG`) with no credential among them (`packages/fx-runner/bin/fx-runner.mjs`). Its output goes only to a local 0600 log; the supervisor reads from it the session id and the outcome, model and token totals of a turn. A halt, or operate turning off, ends the host through the kill path above. A command reaches the host through `engine-host-inbox/`: the host claims it by renaming it before applying anything, writes one outcome file without replacing one that already exists, and a command that already has an outcome is never sent again, also after a restart (`packages/fx-runner/src/engineHost/hostInbox.ts`, `packages/fx-runner/src/engineHost/ticks.ts`). While halted the host applies only `answer_ask`, `pause_loop` and `stop_agent`. Every message the runner sends the host is a fixed template filled with checked values only; the one free text, an owner's note on `answer_ask`, is refused if it holds a bracket, an angle bracket or a lookalike, has control tokens replaced, and goes between the engine's untrusted-content markers (`packages/fx-runner/src/engineHost/prompts.ts`). A second answer for an ask already answered is refused `already_answered` and never reaches the engine; the record is kept 7 days, and a record that cannot be read safely makes the host hold the answer back instead of guessing (`packages/fx-runner/src/engineHost/answered.ts`, #1011). The saved session id is used only when it is a uuid in a file that is not a link and not open to others (`packages/fx-runner/src/engineHost/session.ts`).

## The device-code flow

A machine with no credential can ask to be linked to an account by a code the person types into the browser. The cloud side is merged (#1034, #1035); no source file under `packages/fx-runner` calls it yet. These are the trust rules.

- **Off without a key.** The typed code is hashed with HMAC-SHA256 under `FX_DEVICE_CODE_KEY`, so a leaked table of hashes cannot be searched offline (the code has only about 35 bits, which would otherwise be easy to guess from a leak). A missing value, or one under 32 bytes, answers 503 `not_configured` on start, lookup, approve and deny and stores nothing; the setting is optional and its absence disables the feature (`packages/runner-cloud/src/deviceFlow.ts`, `apps/web/env-manifest.ts`). Changing the key ends every code still waiting.
- **Code formats.** The machine's secret device code is `fxrd_` and 43 characters drawn uniformly from 62, about 256 bits, and only its SHA-256 is stored. The code a person types is eight letters from twenty consonants, shown as `BCDF-GHJK`; the alphabet has no vowel and no digit. Both hashes are 64 lowercase hex characters by CHECK, so a plaintext code cannot be stored (`packages/runner-protocol/src/deviceFlow.ts`, `packages/runner-cloud/src/deviceFlow.ts`, `packages/db/migrations/1036_onboarding_tables.sql`).
- **Proof of possession.** `POST /api/runner/device/start` takes no cookie, token or signature. The caller sends an Ed25519 public key and a compact JWS (`pop`) over this origin, the start path and the time, which must verify against that key with a time within 60 seconds of the server's; a key that is not usable is `invalid_key`, a bad proof `invalid_pop` (`verifyDevicePop` in `packages/runner-protocol/src/deviceFlow.ts`). Every later poll is a signed request by the same key, looked up from the stored key first, and a missing code and a bad signature are the same 401. The database re-checks the key's thumbprint, so a session that calls `runner_device_poll` with a known hash and another key gets nothing (`packages/runner-cloud/src/deviceFlow.ts`, `packages/db/migrations/1037_device_registration.sql`).
- **Start limits.** Ten starts an hour per address (an IPv6 address counts as its /64), plus a global figure of 1,000 an hour unless `FX_DEVICE_FLOW_GLOBAL_PER_HOUR` says otherwise; both are counted on stored rows and a refusal is 429 `rate_limited`. The route also caps 20 starts and 60 polls a minute per address before reading the body (`apps/web/app/api/runner/device/start/handler.ts`, `apps/web/app/api/runner/device/poll/handler.ts`). A poll faster than 5 seconds is 429 `slow_down`.
- **Expiry and single use.** A code lives 10 minutes, fixed in the database by a CHECK on `expires_at` and by `runner_device_start`. Once approved, the next signed poll hands out the registration and marks the code `consumed` in the same statement, so it is handed out once; later polls are 410 `consumed`. A turned-down code is 410 `denied` and an old one 410 `expired`. A pending row has no account until approved, and `app_user` can read only the non-secret columns of rows that belong to its own account (`packages/db/migrations/1036_onboarding_tables.sql`).
- **Who may approve, and the lock.** Lookup, approve and deny are session routes: they name no `principals`, so an API token is refused, and they need the `admin` role (`packages/api/src/routes/runnerDevice.ts`). The definers repeat the check in the database (an owner or admin of an active account, taken from the session's own settings) and take a per-account advisory lock, so attempts for one account are counted one at a time. A typed code that matches nothing is recorded in `runner_device_attempts`; from the sixth in 15 minutes the account's lookups, approvals and cancels all answer 429 `rate_limited` until the window passes. Approve also holds the approver's membership row `FOR SHARE`, so a demotion waits for it and then revokes the runner the call made (`packages/db/migrations/1037_device_registration.sql`).
- **The code goes one way.** The `/link` page reads nothing from its address, so `?code=` never fills the field, and the form shows the machine's facts (hostname, system, country, KVM) beside a fixed warning written by the cloud, not the machine. `confirm` must be the literal `true` to approve. The new runner has no repositories until a project is placed on it (`apps/web/app/link/page.tsx`, `apps/web/app/link/LinkForm.tsx`, `packages/runner-protocol/src/deviceFlow.ts`).

## What is not enforced yet

- Egress enforcement is the sandbox platform's, not this repo's: the repo computes the policy and applies it at create time, but no test here proves that the platform drops everything off the list.
- The install-phase package registries (`registry.npmjs.org`, `npm.pkg.github.com`) are reached directly rather than through the GitHub proxy, and the policy as computed does not distinguish a read (package download) from a write (publish) to either host — flagged as a `TODO` in `packages/runner/src/networkPolicy.ts` itself.
- `apps/web/middleware.ts`'s `sessionStep` headers (`x-fx-user-id`, `x-fx-account-id`) are advisory only: nothing in the repo currently reads them, and they are not revocation-aware (a session bumped by "sign out everywhere" still verifies at the Edge). Real identity must go through `apps/web/lib/shell/session-guard.ts`'s `resolveActiveSession` in a Node-runtime handler.
- The hosted-Postgres owner shape described in the operator runbooks has only been proven against a local cluster built to match Neon's grant; those runbooks state a real Neon branch has never been migrated at HEAD.
