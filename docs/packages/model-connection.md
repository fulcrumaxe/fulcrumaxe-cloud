# model-connection

`@fx/model-connection` is the "bring your own key" package: it lets a tenant store their own AI Gateway or Anthropic API key, validates it against the real provider before ever writing it, encrypts it at rest with envelope encryption, and exposes the narrow read/write/test/remove/mark-broken surface everything else in the platform uses instead of touching key material directly. It has no HTTP route of its own in this package — it is a library other tasks wrap.

## What it does

Four principal-scoped functions cover the whole lifecycle: `connect(ctx, { provider, key })` (`packages/model-connection/src/connect.ts`) validates and stores a new key or rotates an existing one; `getStatus(ctx)` (`summary.ts`) returns the account's connection status without ever returning key material; `test(ctx)` (`validate.ts`) re-validates the stored key against the provider; `remove(ctx)` (`remove.ts`) deletes the row outright. `markBroken`/`markBrokenWithClient`/`createConnectionStatusPort` (`markBroken.ts`) are the write-side entry points other packages (for example `@fx/runner`'s key-failure handling) use to flag a connection broken on a 401/403 without depending on this package's full surface. `markBrokenWithClient` also emits a `model_connection.broken` domain event (`@fx/core`'s `emitDomainEvent`, `#173`) on the same transaction client as its two status-column updates, so the event and the status change commit or roll back together. A connection that turns broken (the 401/403 path, a failed health check, or credits running out) also stamps `model_connections.broken_at` the first time, and a successful validation clears it. Every change made by the connection's own functions (connect, test, remove) also emits `model_connection.changed` (`{ state: ok | broken | unvalidated | removed }`) in the transaction that made it (`validate.ts`, `remove.ts`). The runner's 401/403 path (`markBroken`) emits only `model_connection.broken`, not `.changed`; an open Onboarding window listens for both, so it re-reads either way; onboarding step 1 is derived from that current state, not stamped once.

Every one of the four principal-scoped functions takes a `ModelConnectionCtx`: an `app_user` `pool` (every read/write of key material goes through tenant row-level security on this), a `platformOpsPool` (the only role allowed to write `status`/`last_validated_at`/`last_error_code`), an injectable `httpClient`, and an injectable `kek` (`KekSource`).

## How it works

**Envelope encryption** (`packages/model-connection/src/crypto.ts`). `seal({ kek, aad }, plaintext)` generates a fresh random 32-byte data key (DEK), encrypts the plaintext with it under AES-256-GCM with a random nonce, then wraps that DEK under the caller-supplied `kek` with its own separate AES-256-GCM nonce. Both layers are bound to the same additional authenticated data (`aad`). `open` reverses this and throws `DecryptionFailedError` — never a raw `node:crypto` error — on a tampered ciphertext, a wrong KEK version, or the wrong `aad`; the GCM auth tag length is pinned explicitly (`authTagLength: 16`) so a short or malformed tag is rejected before decryption is attempted, not silently truncated. `fingerprintOf(plaintextKey, kek)` computes an HMAC-SHA256 over the plaintext key, keyed by an HKDF-derived key that is cryptographically distinct from the KEK's own AES key (`fingerprintKeyFrom`, derived via `hkdfSync` with info string `model_key_fingerprint`) — not the KEK directly — truncated to its last 4 hex characters. This fingerprint is display-only; it is never used anywhere in this package to decide whether two keys are "the same."

**Key custody.** The platform key-encryption key (KEK) is supplied through the `KekSource` interface (`packages/model-connection/src/kek.ts`), never hardcoded. The concrete implementation, `envKekSource`, reads a versioned key from the environment: `FX_KEK_V{version}`, base64-encoded, required to decode to exactly 32 bytes, with the current version read from `FX_KEK_CURRENT_VERSION` (default `1`). Each stored connection records the `kek_version` that wrapped its data key, so the platform can rotate its own root key over time without re-encrypting every existing row. This module's own comment notes the KEK is scoped to model connections specifically — `buildAad` binds every ciphertext to `purpose: 'model_key'` — and is not a platform-wide secret shared across other secret categories. The code shows no other place the raw KEK bytes are read from or written to; there is no code path in this package that logs, returns, or otherwise persists the KEK itself.

**What's stored, what isn't.** `connect` (`packages/model-connection/src/connect.ts`) validates a submitted key against the real provider through the injectable `httpClient` *before* any encryption or write happens; a `rejected` outcome (401/403) throws `InvalidModelKeyError` and nothing is ever persisted, encrypted or not. Only `ok`/`network_error` outcomes reach the `INSERT`/`UPDATE`. The row stores `key_ciphertext`, `key_nonce`, `wrapped_dek`, and `kek_version` — never the plaintext, and the `audit_log` write records only the provider and the fingerprint, never key material. `getStatus` (`summary.ts`) reads only `provider`, `key_fingerprint`, `status`, `last_validated_at`, `last_error_code` — its return type, `ConnectionStatusView`, has no field that could carry a key.

**Decrypting on demand.** `test(ctx)` (`validate.ts`) is the one function that decrypts a stored key back to plaintext: it reads the encrypted row through `withTenant` (tenant-scoped), calls `open` with the KEK for that row's recorded `kek_version`, and holds the plaintext only in a local variable for the duration of one HTTP validation call — never logged, returned, or written. A comment guards against a rotation racing this call: `test` and the internal `recordInitialValidation` helper (called by `connect`) both re-check the row's `id` and `key_nonce` under a row lock immediately before writing a validation outcome, skipping the write rather than attaching a stale outcome to a key that was rotated out from under the call; `key_nonce` (fresh random bytes on every `seal()`) is used for this check rather than the 4-character display fingerprint, which the code notes is too collision-prone to gate a correctness check on.

**How a key is proved, and what a rejection means.** One function, `requestFor` (`httpClient.ts`), builds the request that `connect`, the Test key button (`test`) and the daily health job all share, and only the status code of the answer is used: the response body is never read, parsed, stored or logged. It is always a GET of a read endpoint and can never generate. A gateway key is proved with `GET https://ai-gateway.vercel.sh/v1/credits` (Bearer key); the gateway's model listing is never used for it, because the docs say that listing ignores authentication, so it cannot tell a wrong key from a right one. An Anthropic key is proved with `GET https://api.anthropic.com/v1/models` (`x-api-key` plus the pinned `anthropic-version`). Status mapping: any 2xx is ok and 401 is rejected for both providers. 403 is rejected for Anthropic (a `permission_error`), but for the gateway it is a "could not confirm": per the gateway docs a 403 means the endpoint needs a paid plan, not that the key is bad, so it is a network-error outcome with code `403`, never a strike and never broken. 402, 429, any 5xx, a timeout and a failed fetch are also "could not confirm".

**Why neither call costs anything (our reading of the docs, fetched 2026-10-06).** The gateway REST reference (https://vercel.com/docs/ai-gateway/sdks-and-apis/rest-api) lists the credits endpoint as an authenticated read and names no charge for it. The Anthropic rate-limits page (https://platform.claude.com/docs/en/api/rate-limits) defines its limits for the Messages API per model class; the models listing names no model and uses no tokens, so it draws on none of those buckets, and spend is priced per token. Even if a call did count, the job makes one call per connection per 24 hours, far below the lowest published request limit. So the job checks every connection, within its budget, with no "recently used" filter.

**Health checks and the two-strike rule.** `healthCheck(ctx, accountId, connectionId?)` (`validate.ts`, the one export added to the surface frozen in D#31 C6) is the platform's entry point for the `model_key_health` reconcile job (`packages/reconcile/src/jobs/modelKeyHealth.ts`). It takes a context with no principal and no member-role check, reads the sealed key as `app_user` through `withTenant` exactly as `test` does, opens it, makes one validation call, and only then takes the row lock and re-checks `id` and `key_nonce`: a key rotated or replaced meanwhile gets no write at all, strikes included. What it writes is decided by the outcome and `model_connections.health_strikes`. A rejection when the count is 0 sets it to 1 and changes nothing a user can see (no event, no status or error-code change). A rejection when it is 1 or more marks the key broken (`status`, `last_error_code`, `accounts.key_broken_at`, `model_connection.broken` and `model_connection.changed` with state broken, all in one transaction); a connection already broken is left alone so a daily check does not announce it again. A success goes through the ordinary ok path, which also resets the count, as does a user's own successful Test key. A network error changes nothing: strikes are neither added nor reset. A new key resets the count: the guard trigger on `model_connections` clears it whenever the key material or provider changes, and `app_user` cannot write the column itself. `platform_ops` holds SELECT and UPDATE on `health_strikes` only; the key columns stay ungranted. The job runs daily (a `reconcile_jobs` row seeded by migration 0743), 50 connections per run with a cursor, one key open at a time, and records `not_configured` when `DATABASE_URL_APP_USER` or the `FX_KEK_V{n}` key is missing.

**Providers and credential kinds.** A connection holds one credential of a kind (`CREDENTIAL_KINDS` in `packages/model-connection/src/types.ts`): `ai_gateway`, `anthropic`, `openai_api_key`, `codex_access_token` or `chatgpt_oauth`, and each kind belongs to exactly one provider (`ai_gateway`, `anthropic` or `openai`). `connect` takes the provider's API-key kind by default, refuses a kind that does not belong to the provider (`invalid_credential_kind`), and refuses the two plan-based kinds, `codex_access_token` and `chatgpt_oauth` (`kind_not_connectable`): nothing connects them through this function yet. An OpenAI key is proved with `GET https://api.openai.com/v1/models`, a call that, like the other two, uses only the status code.

**Which backend may use which credential** (`packages/model-connection/src/credentialPolicy.ts`). `checkCredentialPolicy` is a closed matrix of agent backend by credential kind by placement (`hosted` or `self_hosted`); anything it does not list is refused, and an unknown backend, kind or placement is named as such. `claude-code` takes `ai_gateway` or `anthropic`; `codex` takes `ai_gateway`, `openai_api_key`, `codex_access_token` and, hosted only, `chatgpt_oauth`; `opencode` takes `ai_gateway` or `openai_api_key`. `admitCredential` runs the matrix first and then, for a plan-based kind, two more checks inside the caller's tenant transaction: the kind's server-side kill switch must be on (`killSwitch.ts`, reads as off when the row is missing, written by `platform_ops` only and audited by a trigger), and the connection must carry an acknowledgement of the current notice version (`noticeAck.ts`; only an owner or admin records one, the row is insert-only, and bumping a version in `NOTICE_VERSIONS` voids older acknowledgements). The refusals are `plan_kind_disabled` and `notice_not_acknowledged`. When a backend is named, `connect` applies the matrix for the hosted placement and refuses a pairing it does not list; it keeps a connection's existing backend when the matrix still allows it for the new kind, else uses `defaultBackendFor` (`claude-code` for gateway and Anthropic keys, `codex` for OpenAI ones).

**Key access** (`packages/model-connection/src/keyAccess.ts`). The one subpath, `@fx/model-connection/keyAccess`, through which an opened key leaves this package. It is deliberately not re-exported from `index.ts`: it reads the sealed key inside `withTenant`, ends that transaction, opens the key, and hands it to a callback, so no database lock is held during the caller's network call and nothing is cached. A non-member gets `NotFoundError`, as with `test`.

**Authorization.** `connect` and `remove` require the caller's role in the account to be `owner` or `admin` (`requireOwnerOrAdmin`); `getStatus` and `test` allow any active member, but both still call `assertActiveMembership` inside the same `withTenant` transaction as the read, so a caller who is not a member of the account gets `NotFoundError` rather than `null` or another account's data.

**Out of credit (D#483 S5-k2).** `creditsExhausted.ts`: `isCreditsExhaustedAnswer({status, text})` reads the three provider answers that mean the customer's own credits ran out (AI Gateway HTTP 402; Anthropic's credit-balance error; OpenAI 429 `insufficient_quota`) and nothing else, and `markCreditsExhausted(platformOpsPool, accountId)` / `markCreditsExhaustedWithClient` record the connection as `status = 'broken'`, `last_error_code = 'credits_exhausted'` (a word, never provider text) without setting `accounts.key_broken_at`: the account keeps running, and `reserve()` refuses only the runs that would draw on the key (`model_credits_exhausted`, which the pipeline shows as a named pause). A connection already broken for a rejected key keeps its own code. `revalidateCreditsExhausted(ctx, accountId, connectionId)` (`validate.ts`) is what the 15-minute reconcile job calls: the same one read-only validation request as the key check (no model named, no tokens), written under the row lock only while the row is still broken for credits; ok makes it `ok` again and the paused items start on their own, a 401 breaks it for that reason, any other answer changes nothing.

## Vercel connection (D#598 P8d-2)

`src/vercelConnection.ts` stores one Vercel API token per account in `vercel_connections` (migration 0885), sealed with the same `seal`/`open` envelope and the same `FX_KEK_V{n}` keys as a model key, but bound to its own AAD purpose (`vercel_token`) so a sealed token cannot be opened as anything else. `connectVercel`, `rotateVercel` and `removeVercel` are owner/admin only and write `vercel_connection.connect|rotate|remove` audit rows (tail of the token only); the token is checked with Vercel first (`createVercelTokenValidator`, through the net-guarded pinned fetch) and a refused or unreachable check stores nothing. Rotation is one row-locked UPDATE of every sealed column. The token is opened in exactly one place, `createSealedVercelCredentials(...).resolve`, the lookup behind the setup-request env-var check; it answers `unavailable` (never an error, never partial) for no connection, a rejected one, a KEK version that is not configured, or a seal that does not open. A 401 from Vercel (and only a 401; a 403 or 404 means this token cannot see that project, which a new token may fix) marks the connection `rejected` through `markRejected`, pinned to the stored token's nonce so a token rotated in meanwhile is never marked. Routes: `GET|POST|PUT|DELETE /api/v1/vercel-connection`; per-state wording is in `src/vercelCopy.ts`. Tests: `test/vercelConnection.test.ts`, `packages/api/test/vercel-connection.test.ts`, `packages/db/test/vercel-connections-schema.test.ts`.

## Hetzner Cloud token (#1057)

`src/machineOps.ts` stores one Hetzner Cloud API token per account in `machine_provider_credentials` (migration 1035), and it is the only reader of it. The token is sealed with the same `seal`/`open` envelope but under its own key, `FX_MACHINE_KEK_V1`, and its own AAD purpose (`hetzner_token`). That key is never the model-connection key and never falls back to it: only version 1 exists, and a missing or malformed value is `machine_kek_unset`, which turns the whole feature off (`/api/health` lists `machine_kek_unset` among its `unconfigured` codes while it is). The value must be canonical base64, padded and with nothing before, inside or after it, of exactly 32 bytes; `parseKek32` in `src/kekFormat.ts` is the one parser, shared with the environment check, so what the check accepts the reader accepts.

- **Connecting.** `POST /api/v1/machine-credentials/hetzner` (session only, owner or admin, body `{token}`, rate-limited like a model key: one try every 10 seconds, 30 an hour per account) checks the machine key, the token's format (64 letters and digits) and that none is connected, then asks Hetzner through `createHetznerCredentialProbe` (`@fx/hetzner`) and seals nothing until the probe says `ok`. It answers 201 with an id, a status, `token_hint` (the last four characters), `unlabelled_server_count` (servers in the project the cloud did not make, a warning only) and `created_at`. The token is never in any response, error, log line or audit row. Errors carry a fixed message and a code from a closed list: `machine_kek_unset` and `not_configured` (503), `invalid_token_format`, `token_invalid` and `token_read_only` (422), `provider_unreachable` (503), `already_connected` (409).
- **Removing.** `DELETE /api/v1/machine-credentials/hetzner` sets the sealed columns to NULL and keeps the row as removed; the account's server rows stay. It answers 204, or 404 `not_connected`, or 409 `credential_in_use` while a server of the account is being deleted with a working token, because that delete's last step needs the token (`refuseWhileDeleting` in `packages/api/src/machines/projectServer.ts`, called from `packages/api/src/routes/machine-credential.ts`, #1284). Replacing a token is this call and then a connect. Both routes write an audit row (`machine_credential.added`, `machine_credential.removed`).
- **Reading it.** `withHetznerToken` (a call that names no server) and `withManagedServer` (a call on one server id, refused `server_not_managed` before the seal is read unless the id is one of the account's `managed_servers`) are the only ways out. Each reads the row, writes the `server.unsealed` audit row, calls the database's `machine_credential_use` and opens the seal inside one transaction, ends it, and then hands the token to a callback, so no lock is held over the Hetzner call. If the audit write, the read or the open fails, the transaction rolls back and the callback never runs. A 401 from Hetzner marks the credential `invalid` (a 403 does not), and later reads answer `credential_invalid` until the token is replaced. A seal that does not open is `unseal_failed`.
- **Sealing the sign-in link and code (#1227).** The same file seals the two secrets of the Claude sign-in link (`createMachineLoginSealer`): the link and the one-time code, each into one blob under the machine key, with `account:request:runner:purpose` as the AAD, so a blob copied to another request, runner or purpose, or another account, fails to open. The blob names the key version that wrapped it, so a rotation still opens old ones. The caller gives the link only to the person's own response and the code only to the runner's one fetch.
- **Reading one server (#1232).** `packages/api/src/machines/actions.ts` calls `withManagedServer` for a reboot and for deleting an orphan, so the token is opened for that one Hetzner server id, and an id that is not one of the account's servers is refused before the seal is read.
- **What keeps it narrow.** `test/machineOps.static.test.ts` pins that `machineOps.ts` is the only file that reads `FX_MACHINE_KEK_V1`, the only caller of `machine_credential_use` and the only writer of the `server.unsealed` audit action. A Hetzner token shape (64 letters and digits with no prefix, and not all hex, so a sha-256 digest is kept) is also redacted from run events and runner telemetry.
- **Who calls the readers.** `packages/api/src/routes/machine-credential.ts` calls the connect and remove paths, and `packages/api/src/machines/servers.ts` calls `withHetznerToken` to quote and create a Hetzner server with the stored token (#1177). A create that may have landed without an answer is refused 503 `server_outcome_unknown` rather than passed through as the cause that interrupted it (`packages/api/src/machines/servers.ts`, #1240). When a different token is connected than the one that made a server, the delete path (`ensureCredential` in `packages/api/src/machines/lifecycle.ts`) reads Hetzner through the connected token with `withHetznerClient` from `packages/api/src/machines/servers.ts`, and moves the server's row onto it only if the server carries the cloud's labels and the row's id (#1284). `test/machineOps.static.test.ts` lists those two files, with the package index and the generated client, as the only users of the machine-ops names.

## Security notes

See `../security.md` for the platform-wide model; this package is one of the two places (alongside `@fx/runner`'s firewall-policy step) that ever holds a tenant's model key in plaintext, and both hold it only for the duration of one operation, in a local variable, never assigned to a return value or a broader scope. `connect.ts` rejects a key containing non-printable-ASCII characters or surrounding whitespace before any network call, so a key shaped in a way that could break an HTTP header is refused before it is ever encrypted or stored. `connect` also checks the requested `provider` against an exact allowed set (`ai_gateway`, `anthropic`, `openai`) before doing anything else with it, so an unrecognized provider value can never reach the code path that sends a key to `api.anthropic.com`.

**Reading the screen (D#598 P8d-3a).** `GET /api/v1/vercel-connection/details` (session-only, any member) is the read side of the connection screen: `state` (`not_connected`, `connected`, `revoked_or_expired`), `names` (the Vercel team's display name and the project names the token sees, or `{status: "unavailable"}`; never ids, never a partial answer) and `check` (what the latest env-var check said about the token, with a sentence naming the project). `revoked_or_expired` is derived from the latest check since the token was last connected or replaced (`packages/core/src/setup-requests/latestCheck.ts`), so replacing the token clears it with no write. Names come from `packages/core/src/setup-requests/vercelNames.ts` through the pinned fetch (`GET /v2/teams/<team id>` and the first page of `GET /v10/projects`), cached per account and credential (5 minutes; 30 seconds for a failure). It is a separate route so the status read stays a database read and a Vercel outage cannot fail it. Tests: `packages/api/test/vercel-connection-details.test.ts`, `packages/core/test/setup-requests/vercelNames.test.ts`.

## Tests

Run with `pnpm --filter @fx/model-connection test` (`bash scripts/test-pg.sh`) — every suite in this package runs against a real Postgres instance via `test/globalSetup.ts`, with `fileParallelism: false` and a single forked worker (`test/toctou.test.ts` deliberately holds a row lock open across a concurrent write, which parallel files sharing the database would corrupt). `test/crypto.test.ts` covers `seal`/`open`/`fingerprintOf` directly, including the HKDF fingerprint-key derivation. `test/toctou.test.ts`, `test/w1-nonce-rotation-check.test.ts`, and `test/pool-deadlock.test.ts` cover the concurrency/rotation races described above. `test/httpClientProviders.test.ts` runs the real client against local TLS servers that stand in for the two providers (`test/helpers/strictProviders.ts`): they refuse any method but GET and any path but the one allowed, which a test asserts after every case. `test/healthCheck.pg.test.ts` covers the strike rule, the rotation reset and the grants. `test/own-cluster.test.ts` and `test/tenant-and-broken.test.ts` cover the account-status pause/restore behavior. A test that seeds an account with a hosted plan also sets `hosted_plan_paid = true` (`accounts.hosted_plan_paid`, migration 1048): hosted entitlements now read that flag, not the plan name alone.

## Known gaps

The Anthropic provider is gated behind `isAnthropicProviderEnabled()` (`packages/model-connection/src/types.ts`), hardcoded to return `false` pending a dependency this package's own comment names as a future spike — so a tenant cannot connect an Anthropic-provider key through this package today even though the code path exists and is tested. The plan-based credential kinds are defined, and policed at admit, but have no connect path yet.
