# runner

`@fx/runner` orchestrates one agent run's sandbox lifecycle: it decides which network destinations a role's sandbox may reach, names and retains the sandbox, decrypts the tenant's model key for exactly as long as it takes to build a network policy from it, and drives the `agent_runs` status state machine from `pending` through to a terminal outcome. It is the package that turns "start this role against this repo" into a real (or, today, fake) sandboxed process.

Sources:

- `packages/net-guard/src/`

## What it does

`startAgentRun` (`packages/runner/src/startAgentRun.ts`) resolves a repo's `execution_mode` column, inserts a `pending` `agent_runs` row, asks an `ExecutionTarget` to admit the run against the tenant's spend budget, then races `dispatch` against a queue time-to-live (`QUEUE_TTL_MS`, 15 minutes by default). The run lands on `refused_spend`, `timed_out`, `failed`, or `running`. `cancelRun` (`packages/runner/src/cancelRun.ts`) is the counterpart a request handler calls to stop a run at any point; it is idempotent and returns the run's settled/released spend totals either way.

Today `SandboxTarget` (`packages/runner/src/targets/sandboxTarget.ts`) is the only registered `ExecutionTarget` (`packages/runner/src/executionTarget.ts`'s `EXECUTION_TARGETS` map has exactly one entry, `sandbox`). It wraps `SandboxPort`, `buildFirewallPolicy`, `buildSandboxEnv`, and `@fx/spend`'s `reserve`/`release`, and is the only file in `packages/runner/src` allowed to import any of those — `packages/runner/test/importBoundary.test.ts` enforces that `startAgentRun.ts`/`cancelRun.ts` reach the sandbox only through the target-agnostic `ExecutionTarget` interface, never sandbox internals directly.

## How it works

**Sandbox network policy.** `networkPolicy(role, product, connection, phase)` in `packages/runner/src/networkPolicy.ts` returns a finite, explicit allowlist and never a wildcard rule — enforced by a test that iterates every role/product/provider combination. The allowed destinations are: the tenant's model host (`ai-gateway.vercel.sh` for the `ai_gateway` provider, `api.anthropic.com` for `anthropic`, keyed off `MODEL_HOST_BY_PROVIDER`, never both at once), the installation's own GitHub-proxy forward host (`connection.githubForwardHost`, validated by `assertStrictGithubForwardHost` against a strict lowercase-ASCII hostname pattern and a reserved-name list so it can never resolve to a model host, a package registry, or `github.com`/`githubusercontent.com` themselves), and, only when `phase === "install"`, the two `INSTALL_PHASE_REGISTRY_ALLOWLIST` hosts (`registry.npmjs.org`, `npm.pkg.github.com`). A code comment on that registry allowlist notes it is still reachable directly rather than through the proxy, and still accepts publishes during the install window, not just installs — left as a known gap rather than fixed in this package.

The function itself only builds the list; nothing in `packages/runner` enforces that a sandbox actually treats the list as deny-by-default at the network layer — that enforcement is a firewall component this package does not contain (see Known gaps).

**Sandbox naming.** `sandboxNameFor` (`packages/runner/src/sandboxNaming.ts`) gives every non-executor role a fresh, run-scoped name (`rn-{role.length}-{role}-{runId}`) with no persistence (`retentionPolicyFor` returns `{ persistent: false }`). The `executor` role is the one exception: its sandbox name is `ex-{accountId}-{repoId}-{pr}`, stable across a PR's whole lifetime, with `persistent: true` and `keepLastSnapshots: 1`, so a later run for the same PR can resume the same sandbox. Both `accountId` and `repoId` are validated as UUIDs and `pr` as a positive safe integer before the name is built — a code comment on this function explains that folding the account into the name closes a cross-tenant sandbox-name-collision path a prior revision of PR #85 left open when only `repoId` (a caller-choosable, reusable UUID) was used. `PR_EVENTS_THAT_DELETE_SANDBOX` names the two GitHub events (`pr.closed`, `pr.merged`) that must delete an executor's persistent sandbox; nothing in this package's own code calls that deletion — it is a named contract for the caller that owns the webhook.

**Real vs. fake.** `SandboxPort` (`packages/runner/src/sandboxPort.ts`) is an interface only — no production implementation ships in this package. `createFakeSandbox` (`packages/runner/src/fakeSandbox.ts`) is the one implementation that exists: it wraps a caller-supplied `AgentRuntime` from `@fx/runtime` (or a hand-written stub), records every `createSandbox`/`startDetached`/`extendTimeout`/`stop`/`resume`/`deleteSandbox` call on a `state` object tests assert against, and lets a test force a sandbox to "hang" (its hook never fires) or fail a `resume` with `SandboxNotFoundError`. `ExecutionTarget` (`packages/runner/src/executionTarget.ts`) is the seam between the two: it is what `startAgentRun`/`cancelRun` depend on, and `SandboxTarget` is the only adapter built against it — `resolveExecutionTarget` looks a mode up in a caller-supplied registry and throws `UnknownExecutionModeError` for anything unregistered, before any reservation or database write happens.

**GitHub forward host allowlist.** `loadGithubForwardConfig(env)` (`packages/runner/src/githubForwardConfig.ts`) is the only function that produces a `GithubForwardConfig`: it reads exactly `FX_GH_FORWARD_SUFFIX` and `FX_GH_FORWARD_HOST` from a caller-supplied env object (never `process.env`, never a DB row or tenant setting), and accepts a host only if it passes the same strict-hostname/reserved-name checks `networkPolicy.ts` already enforced, plus a new one: the host must equal the operator-configured suffix or sit under it on a label boundary. The returned object is frozen and branded with a module-private symbol so nothing outside the file can construct one by object literal; `assertGithubForwardConfig` re-checks a value's brand (against a private `WeakSet` of every config the loader has actually issued, not just the symbol, which is recoverable via `Object.getOwnPropertySymbols`) and re-validates its `host`/`suffix` at runtime, so a value forged past the type system is still refused.

**Firewall-policy step.** `buildFirewallPolicy` (`packages/runner/src/firewallPolicy.ts`) is the one function in this package that ever touches a tenant's decrypted model key. Before decrypting anything, it reads its injected `deps.githubForward` into a local exactly once, asserts it with `assertGithubForwardConfig`, and resolves its host through `@fx/net-guard`'s `resolveChecked` (`packages/net-guard/src/resolveChecked.ts`) on every call — never cached — refusing with `GithubForwardHostRefusedError` (`class: "config" | "dns_failed" | "blocked_address"`, never the resolved address) before `decryptTenantKey` is ever called if either check fails. `@fx/net-guard`'s `isBlockedAddress` (`packages/net-guard/src/blockedAddress.ts`) is the classifier `resolveChecked` runs every resolved address through: an RFC 5737/6598/etc. blocked-range check (loopback, private, link-local, metadata, multicast, reserved), including the three ways an IPv4 address can hide inside an IPv6 literal (IPv4-mapped, NAT64, 6to4). Once both checks pass, `buildFirewallPolicy` calls the caller-injected `DecryptTenantKey`, uses the plaintext only to confirm decryption succeeded, and returns `NetworkPolicyRule[]` — a host and a header name, never the key value. The plaintext lives only on this function's own stack for the duration of the decrypt call.

**Per-role tool permissions (owner ruling, D#483 P3; amends C59 SS-CONTENT and C66).** The settings file used to hold the runner's hook and an empty `permissions` entry, so a fresh print-mode run relied on the CLI's implicit default and a RESUMED run (an executor fix round) was refused every edit and every command of the version control tool, because that default does not carry over to `--resume`. `agentSettingsFor(role)` now writes, for every role and for a start and a resume alike, the hook plus an explicit allow list and `defaultMode: "dontAsk"` (anything not on the list is refused, never asked about): the executor may read, edit and write, run git, node and the package managers, curl and do basic file operations; the code and security reviewers, the acceptance tester and the debater may read, run git, node and the test runners, with no edit or write tool and no curl; every other role may read, curl, run git and use read-only helpers. A role the lists do not name gets the narrowest list. `test/agentPermissions.test.ts` pins each list literally and `packages/worker/test/agentRolesParity.test.ts` pins the manifest to them. These lists are least privilege on top of the real boundary (the sandbox VM, the egress firewall and the gh-proxy's push and pull-request rules), not a replacement for it: a shell command a role may run (`node`, `git`, a test runner) can still write files in the sandbox, so "no edits" for a reviewer means no edit tool, not a read-only filesystem. That `dontAsk` with an allow list behaves the same on `--resume` as on a start was checked by the team lead locally on CLI 2.1.289; the version the runner accepts is `CLAUDE_CLI_VERSION`.

**Agent config (H14c-SS).** The sandbox agent loads configuration only from files the runner writes, never from the customer's checkout.
`vercelSandboxPort.ts`'s `SANDBOX_AGENT_COMMAND` passes an empty `--setting-sources` (no user, project or local settings file),
`--settings /fx/agent-config/settings.json`, `--strict-mcp-config` and `--mcp-config /fx/agent-config/mcp.json`. Before every start and resume the
runner rewrites both files read-only from `agentConfig.ts` (the role's tool allow list and `defaultMode: "dontAsk"`, no MCP servers) and one script, `limit-hook.sh` (0444, C66). That script
is the only hook: it uses shell builtins only, reads precomputed values from `/fx/run-limits.json` and prints an advisory run-limit warning, so a repo
config still adds no hook. `launch()` refuses a workdir equal to, under or containing `/fx/agent-config`. Mechanism (a) was chosen because the
pinned CLI 2.1.0 accepts an empty `--setting-sources` and always adds the `--settings` file on top, so no `CLAUDE_CONFIG_DIR` is needed. Project
settings, `.mcp.json`, commands, agents, skills, output styles and the `CLAUDE.md` variants do not load. RESIDUAL (C63, from the `cli.js` text;
H18-SS1b measures it live): `.claude/rules/*.md` DO load as unfenced, text-only memory when the agent reads a file (every rule between the workdir
and that file, plus rules with `globs` from the workdir upward); they add no hooks, permissions, MCP or env, and H14c-SS-2 removes them where the
CLI allows. RESIDUAL (C66, H18-SS2): with hooks enabled, managed-policy hooks now run (the image's managed-settings file, or a cached remote-settings
file under `~/.claude`), and a same-uid earlier command could plant one. Same-uid residuals, under C44 R5 and bounded by no credential in the VM
and egress: a background process from an earlier command can race the per-start rewrite (0444 does not stop the same uid); `~/.claude.json` is read
whatever the sources are; `--resume` reloads a transcript under `~/.claude/projects/` that an earlier command can edit. Managed settings are
H18-SS2. `test/hostileConfig.contract.ts` is the per-backend conformance test against `test/fixtures/hostile-repo/`; every new backend registers with it.

**Run state machine.** `packages/runner/src/statusTransitions.ts` owns the legal `agent_runs.status` and `work_items.state` vocabularies and their transition graphs (`RUN_STATUS_TRANSITIONS`, `WORK_ITEM_STATE_TRANSITIONS`), since the `packages/db` migration that creates these columns leaves them as unconstrained `text`. `runStatusWriter.ts`'s `writeRunStatus` is the single compare-and-set writer for `agent_runs.status`: one `UPDATE ... WHERE status = $from`, and a losing race (`rowCount === 0`) re-reads and returns the row's actual current status rather than retrying or overwriting. A successful write also inserts a `run_events` row in the same transaction. `insertAgentRun` is the only `agent_runs` INSERT in the package.

**Mid-run metering, key failure, resume (`#171`).** `SandboxTarget`'s private `meterModelUnderLock` runs on every model event `dispatch`/`resume` forwards through `onEvent`: `modelFailure.ts`'s `detectModelFailure` reads a fake or real 401/402/403 out of an error event's text, and any of the three stops the run, while 401/403 specifically also call `ConnectionStatusPort.markBroken` (`@fx/model-connection`) to flag the tenant's model connection broken and pause its other queued runs — 402/`quota_for_entity_exceeded` is treated as a budget problem, not a bad key, so it does not call `markBroken`. Crossing the per-spawn cap or the model budget mid-run kills the run with status `killed_spend`, settling its real metered cost under the same account+model advisory lock `@fx/spend`'s `settleWith`/`releaseWith` already use, so a concurrent cancel and a concurrent metered kill can't both write a ledger row for the same reservation. `SandboxTarget.resume` reuses the same sandbox name and passes `--resume <sessionId>` for an executor's fix-round retry, falling back to a fresh dispatch on `SandboxNotFoundError`.

**The watchdog (`hookChannel.ts`, `workflows/agentRun.ts`, `#171`/`#174`).** A post-dispatch watchdog — distinct from `startAgentRun`'s own queue-TTL — races a hook wait against a timeout so a dispatched run that never resumes its hook is not stuck forever. `hookChannel.ts`'s `HookWaitPort`/`HookResumeSink` are a structurally-identical pair to `targets/sandboxTarget.ts`'s own `HookResumePort`, kept in a separate file specifically so `workflows/agentRun.ts` never has to import sandbox internals (`test/importBoundary.test.ts` enforces this). `workflows/agentRun.ts`'s `agentRunWorkflow` is now a real `"use workflow"` entrypoint (the stable `workflow` npm package, `#174`) whose dispatch/hook-wait/timeout/cancel/finalize steps are each a `"use step"` wrapper over the already-tested logic above, and the watchdog leg races a real durable `sleep()` instead of an injected `setTimeout`. `hookWaitStep` still wraps `hookChannel.ts`'s in-memory `HookWaitPort`, not a real Workflow `createHook()`/`resumeHook()` pair, and nothing calls `agentRunWorkflow` from a deployed endpoint yet — both are named as follow-on work in the file's own header.

**The run-funding seam (`funding.ts`, `#171`).** Every spend/key call `SandboxTarget` makes resolves its payer account through `resolvePayer` (default: `defaultResolvePayer`) rather than assuming the run's own account: `{ kind: "self" }` (or no `funding` at all) resolves to `run.accountId`; `{ kind: "claim" }` throws `UnsupportedFundingError` unconditionally, since the claim-funded-run feature this seam anticipates is not built. The `agent_runs`/`run_events` writes themselves always use the run's own account regardless of funding.

## Data it touches

`agent_runs`, `run_events`, and (via `@fx/spend`) `spend_reservations` and `ledger`. See `../data-model.md` for the schema.

## Security notes

See `../security.md` for the platform-wide model. Package-specific points: `packages/runner/src/sandboxEnv.ts`'s `buildSandboxEnv` takes no ambient input (no `process.env`, no credential object) and returns only two placeholder values (`ANTHROPIC_API_KEY=""`, `ANTHROPIC_AUTH_TOKEN="brokered-at-firewall"`); `isForbiddenSandboxEnvName` fails closed on any candidate name that isn't even a well-formed env-var identifier (`^[A-Za-z_][A-Za-z0-9_]*$`, catching a leading/trailing space or a hyphen) before testing whether it otherwise matches any other var name shaped like a credential (`FORBIDDEN_ENV_NAME_PATTERN`, which also now matches `PEM` at a name boundary on both sides — e.g. `APP_PEM_FILE`, `PEM_DIR` — not only as a trailing segment). The GitHub forward host that reaches the sandbox's firewall rule is resolved and address-checked by `@fx/net-guard` (see "How it works" above) before a policy is ever built, so a forward host that resolves to a loopback/private/link-local/metadata/multicast/reserved address is refused rather than allowlisted. `SandboxTarget` (`packages/runner/src/targets/sandboxTarget.ts`) carries several rounds of concurrency fixes from PR #85's later revisions, addressing races between a cancel/timeout and an in-flight `dispatch`: it re-checks the run's durable `pending` status after `createSandbox`, again immediately before `startDetached`, and tracks per-instance bookkeeping (`started`, `cancelRequested`, `stoppedDirectly`) so a cancel that lands on the same instance stops the sandbox directly rather than through a reservation table a competing writer may have already emptied. `cancel`'s `stillOwnsSandbox` check also guards against a stale instance stopping a newer run that has since taken over a persistent (executor) sandbox's shared name.

## Known gaps

- No production `SandboxPort` implementation exists in this package — only the interface and the fake (`packages/runner/src/sandboxPort.ts`'s own header, `packages/runner/src/fakeSandbox.ts`).
- `C15`/`C26` (`#171`'s own deferred scope): no real `@vercel/sandbox`-backed `SandboxPort` and no production composition root that actually calls `startAgentRun`/`agentRunWorkflow` from a deployed endpoint yet.
- `workflows/agentRun.ts`'s `agentRunWorkflow` (`#174`) is real Workflow-SDK code, but its `hookWaitStep` still wraps `hookChannel.ts`'s in-memory `HookWaitPort` rather than a real `createHook()`/`resumeHook()` pair, and its `pool`/`registry`/`hookWait` constructor-style parameters are not yet the serializable-only entrypoint a real composition root would need (both named as H14 follow-on work in the file's own header).
- `funding.ts`'s claim-funded run support (`{ kind: "claim" }`) fails closed with `UnsupportedFundingError` — the feature it anticipates (D#70) is not built.
- `SandboxTarget.admit` (`packages/runner/src/targets/sandboxTarget.ts`) calls `@fx/spend`'s `reserve` in its own transaction rather than the caller's, so the spend reservation and the `agent_runs` insert do not commit atomically yet; the `client` parameter is accepted but unused, documented as a seam for a future shared-transaction version of `reserve`.
- `INSTALL_PHASE_REGISTRY_ALLOWLIST` hosts are reached directly rather than through the GitHub proxy, and accept publishes as well as installs during the install phase — noted as a `TODO` in `packages/runner/src/networkPolicy.ts` pending a real firewall component.
- `loadGithubForwardConfig` (`packages/runner/src/githubForwardConfig.ts`) is now called in production (`#140`) — once, at module scope, in the gh-proxy route (`apps/web/app/api/gh-proxy/[...path]/route.ts`), for that route's own OIDC-audience/host-binding checks (`githubProxyForwardUrl`, `#160`). It is still not wired into `SandboxTarget`'s `deps.githubForward` / `buildFirewallPolicy`'s `deps.githubForward` — those still take a caller-injected `GithubForwardConfig`, and no production composition root exists yet to supply a real one (see the `C15`/`C26` gap above).
