# runner

`@fx/runner` orchestrates one agent run's sandbox lifecycle: it decides which network destinations a role's sandbox may reach, names and retains the sandbox, decrypts the tenant's model key for exactly as long as it takes to build a network policy from it, and drives the `agent_runs` status state machine from `pending` through to a terminal outcome. It is the package that turns "start this role against this repo" into a real (or, today, fake) sandboxed process.

## What it does

`startAgentRun` (`packages/runner/src/startAgentRun.ts`) resolves a repo's `execution_mode` column, inserts a `pending` `agent_runs` row, asks an `ExecutionTarget` to admit the run against the tenant's spend budget, then races `dispatch` against a queue time-to-live (`QUEUE_TTL_MS`, 15 minutes by default). The run lands on `refused_spend`, `timed_out`, `failed`, or `running`. `cancelRun` (`packages/runner/src/cancelRun.ts`) is the counterpart a request handler calls to stop a run at any point; it is idempotent and returns the run's settled/released spend totals either way.

`EXECUTION_TARGETS` (`packages/runner/src/executionTarget.ts`) registers one `ExecutionTarget` per execution mode: `sandbox` is `SandboxTarget` (`packages/runner/src/targets/sandboxTarget.ts`), `runner_local` is `RunnerTarget` (`packages/runner/src/targets/runnerTarget.ts`, a run that waits in `pending` for a runner on the customer's machine to claim it, holding no spend reservation), and `runner_verified` is `VerifiedTarget` (`packages/runner/src/targets/verifiedTarget.ts`), which wraps a `RunnerTarget` and the sandbox target. `SandboxTarget` wraps `SandboxPort`, `buildFirewallPolicy`, `buildSandboxEnv`, and `@fx/spend`'s `reserve`/`release`, and is the only file in `packages/runner/src` allowed to import any of those — `packages/runner/test/importBoundary.test.ts` enforces that `startAgentRun.ts`/`cancelRun.ts` reach the sandbox only through the target-agnostic `ExecutionTarget` interface, never sandbox internals directly.

## How it works

**Sandbox network policy.** `networkPolicy(role, product, connection, phase)` in `packages/runner/src/networkPolicy.ts` returns a finite, explicit allowlist and never a wildcard rule — enforced by a test that iterates every role/product/provider combination. The allowed destinations are: the tenant's model host (`ai-gateway.vercel.sh` for the `ai_gateway` provider, `api.anthropic.com` for `anthropic`, keyed off `MODEL_HOST_BY_PROVIDER`, never both at once), the installation's own GitHub-proxy forward host (`connection.githubForwardHost`, validated by `assertStrictGithubForwardHost` against a strict lowercase-ASCII hostname pattern and a reserved-name list so it can never resolve to a model host, a package registry, or `github.com`/`githubusercontent.com` themselves), and, only when `phase === "install"`, the two `INSTALL_PHASE_REGISTRY_ALLOWLIST` hosts (`registry.npmjs.org`, `npm.pkg.github.com`). A code comment on that registry allowlist notes it is still reachable directly rather than through the proxy, and still accepts publishes during the install window, not just installs — left as a known gap rather than fixed in this package.

The function itself only builds the list; nothing in `packages/runner` enforces that a sandbox actually treats the list as deny-by-default at the network layer — that enforcement is a firewall component this package does not contain (see Known gaps).

**Sandbox naming.** `sandboxNameFor` (`packages/runner/src/sandboxNaming.ts`) gives every non-executor role a fresh, run-scoped name (`rn-{role.length}-{role}-{runId}`) with no persistence (`retentionPolicyFor` returns `{ persistent: false }`). The `executor` role is the one exception: its sandbox name is `ex-{accountId}-{repoId}-{pr}`, stable across a PR's whole lifetime, with `persistent: true` and `keepLastSnapshots: 1`, so a later run for the same PR can resume the same sandbox. Both `accountId` and `repoId` are validated as UUIDs and `pr` as a positive safe integer before the name is built — a code comment on this function explains that folding the account into the name closes a cross-tenant sandbox-name-collision path a prior revision of PR #85 left open when only `repoId` (a caller-choosable, reusable UUID) was used. `PR_EVENTS_THAT_DELETE_SANDBOX` names the two GitHub events (`pr.closed`, `pr.merged`) that must delete an executor's persistent sandbox; nothing in this package's own code calls that deletion — it is a named contract for the caller that owns the webhook.

**Real vs. fake.** `SandboxPort` (`packages/runner/src/sandboxPort.ts`) is an interface only — no production implementation ships in this package. `createFakeSandbox` (`packages/runner/src/fakeSandbox.ts`) is the one implementation that exists: it wraps a caller-supplied `AgentRuntime` from `@fx/runtime` (or a hand-written stub), records every `createSandbox`/`startDetached`/`extendTimeout`/`stop`/`resume`/`deleteSandbox` call on a `state` object tests assert against, and lets a test force a sandbox to "hang" (its hook never fires) or fail a `resume` with `SandboxNotFoundError`. `ExecutionTarget` (`packages/runner/src/executionTarget.ts`) is the seam between the two: it is what `startAgentRun`/`cancelRun` depend on, and `SandboxTarget` is the only adapter built against it — `resolveExecutionTarget` looks a mode up in a caller-supplied registry and throws `UnknownExecutionModeError` for anything unregistered, before any reservation or database write happens.

**GitHub forward host allowlist.** `loadGithubForwardConfig(env)` (`packages/runner/src/githubForwardConfig.ts`) is the only function that produces a `GithubForwardConfig`: it reads exactly `FX_GH_FORWARD_SUFFIX` and `FX_GH_FORWARD_HOST` from a caller-supplied env object (never `process.env`, never a DB row or tenant setting), and accepts a host only if it passes the same strict-hostname/reserved-name checks `networkPolicy.ts` already enforced, plus a new one: the host must equal the operator-configured suffix or sit under it on a label boundary. The returned object is frozen and branded with a module-private symbol so nothing outside the file can construct one by object literal; `assertGithubForwardConfig` re-checks a value's brand (against a private `WeakSet` of every config the loader has actually issued, not just the symbol, which is recoverable via `Object.getOwnPropertySymbols`) and re-validates its `host`/`suffix` at runtime, so a value forged past the type system is still refused.

**Firewall-policy step.** `buildFirewallPolicy` (`packages/runner/src/firewallPolicy.ts`) is the one function in this package that ever touches a tenant's decrypted model key. Before decrypting anything, it reads its injected `deps.githubForward` into a local exactly once, asserts it with `assertGithubForwardConfig`, and resolves its host through `@fx/net-guard`'s `resolveChecked` (`packages/net-guard/src/resolveChecked.ts`) on every call — never cached — refusing with `GithubForwardHostRefusedError` (`class: "config" | "dns_failed" | "blocked_address"`, never the resolved address) before `decryptTenantKey` is ever called if either check fails. `@fx/net-guard`'s `isBlockedAddress` (`packages/net-guard/src/blockedAddress.ts`) is the classifier `resolveChecked` runs every resolved address through: an RFC 5737/6598/etc. blocked-range check (loopback, private, link-local, metadata, multicast, reserved), including the three ways an IPv4 address can hide inside an IPv6 literal (IPv4-mapped, NAT64, 6to4). Once both checks pass, `buildFirewallPolicy` calls the caller-injected `DecryptTenantKey`, uses the plaintext only to confirm decryption succeeded, and returns `NetworkPolicyRule[]` — a host and a header name, never the key value. The plaintext lives only on this function's own stack for the duration of the decrypt call.

**Per-role tool permissions (owner ruling, D#483 P3; amends C59 SS-CONTENT and C66).** The settings file used to hold the runner's hook and an empty `permissions` entry, so a fresh print-mode run relied on the CLI's implicit default and a RESUMED run (an executor fix round) was refused every edit and every command of the version control tool, because that default does not carry over to `--resume`. `agentSettingsFor(role)` now writes, for every role and for a start and a resume alike, the hook plus an explicit allow list and `defaultMode: "dontAsk"` (anything not on the list is refused, never asked about): the executor may read, edit and write, run git, node and the package managers, curl and do basic file operations; the code and security reviewers, the acceptance tester and the debater may read, run git, node and the test runners, with no edit or write tool and no curl; every other role may read, curl, run git and use read-only helpers. A role the lists do not name gets the narrowest list. `test/agentPermissions.test.ts` pins each list literally and `packages/worker/test/agentRolesParity.test.ts` pins the manifest to them. These lists are least privilege on top of the real boundary (the sandbox VM, the egress firewall and the gh-proxy's push and pull-request rules), not a replacement for it: a shell command a role may run (`node`, `git`, a test runner) can still write files in the sandbox, so "no edits" for a reviewer means no edit tool, not a read-only filesystem. That `dontAsk` with an allow list behaves the same on `--resume` as on a start was checked by the team lead locally on CLI 2.1.289; the version the runner accepts is `CLAUDE_CLI_VERSION`.

**Agent config (H14c-SS).** The sandbox agent loads configuration only from files the runner writes, never from the customer's checkout.
`vercelSandboxPort.ts`'s `SANDBOX_AGENT_COMMAND` passes an empty `--setting-sources` (no user, project or local settings file),
`--settings /fx/agent-config/settings.json`, `--strict-mcp-config` and `--mcp-config /fx/agent-config/mcp.json`. Before every start and resume the
runner rewrites both files read-only from `agentConfig.ts` (the role's tool allow list and `defaultMode: "dontAsk"`, no MCP servers) and one script, `limit-hook.sh` (0444, C66). That script
is the only hook: it uses shell builtins only, reads precomputed values from `/fx/run-limits.json` and prints an advisory run-limit warning, so a repo
config still adds no hook. `launch()` refuses a workdir equal to, under or containing `/fx/agent-config`. Mechanism (a) was chosen because the
pinned CLI 2.1.0 accepts an empty `--setting-sources` and always adds the `--settings` file on top, so no `CLAUDE_CONFIG_DIR` is needed. Project
settings, `.mcp.json`, commands, agents, skills, output styles and the `CLAUDE.md` variants do not load. RESIDUAL (C63, from the `cli.js` text;
H18-SS1b measures it live): `.claude/rules/*.md` DO load as unfenced, text-only memory when the agent reads a file (every rule between the workdir
and that file, plus rules with `globs` from the workdir upward); they add no hooks, permissions, MCP or env, and H14c-SS-2 removes them where the
CLI allows. RESIDUAL (C66, H18-SS2): with hooks enabled, managed-policy hooks now run (the image's managed-settings file, or a cached remote-settings
file under `~/.claude`), and a same-uid earlier command could plant one. Same-uid residuals, under C44 R5 and bounded by no credential in the VM
and egress: a background process from an earlier command can race the per-start rewrite (0444 does not stop the same uid); `~/.claude.json` is read
whatever the sources are; `--resume` reloads a transcript under `~/.claude/projects/` that an earlier command can edit. Managed settings are
H18-SS2. `test/hostileConfig.contract.ts` is the per-backend conformance test against `test/fixtures/hostile-repo/`; every new backend registers with it. `test/hostileConfig.test.ts` runs it with the clock held still, because the run-limits file carries the run's start time and two runs straddling a millisecond tick would otherwise differ in that one number (#969).

**Run state machine.** `packages/runner/src/statusTransitions.ts` owns the legal `agent_runs.status` and `work_items.state` vocabularies and their transition graphs (`RUN_STATUS_TRANSITIONS`, `WORK_ITEM_STATE_TRANSITIONS`), since the `packages/db` migration that creates these columns leaves them as unconstrained `text`. `runStatusWriter.ts`'s `writeRunStatus` is the single compare-and-set writer for `agent_runs.status`: one `UPDATE ... WHERE status = $from`, and a losing race (`rowCount === 0`) re-reads and returns the row's actual current status rather than retrying or overwriting. A successful write also inserts a `run_events` row in the same transaction. `insertAgentRun` is the only `agent_runs` INSERT in the package. When the run that just ended is a post-merge tester run (role `deploy-verifier`), `writeRunStatusOn` also wakes the verify stage: it sets the `proposal-verify-sweep` pending-work marker and sends the sweep's signed kick (`packages/core/src/verify/wake.ts`), so the stage does not wait for its next scheduled tick. No other role's end does this.

**Which roles a Local-only repository serves.** `RunnerTarget`'s `admit` refuses a run before anything is counted or written when its role cannot run on the runner. In a `runner_local` repository the confined read-only roles are refused (`role_not_runner_eligible`), except two: the deploy verifier and the proposal verifier (`proposal-verifier`), whose cites our cloud re-reads at the pinned sha for now. The discovery analyst stays refused there. The runner's progress projection can also project a `base_updated` stage, next to `deps_installed` and `deps_install_failed` (`packages/runner/src/runnerProgress.ts`).

**Mid-run metering, key failure, resume (`#171`).** `SandboxTarget`'s private `meterModelUnderLock` runs on every model event `dispatch`/`resume` forwards through `onEvent`: `modelFailure.ts`'s `detectModelFailure` reads a fake or real 401/402/403 out of an error event's text, and any of the three stops the run, while 401/403 specifically also call `ConnectionStatusPort.markBroken` (`@fx/model-connection`) to flag the tenant's model connection broken and pause its other queued runs — an out-of-credit answer (D#483 S5-k2: AI Gateway 402/`quota_for_entity_exceeded`, Anthropic's credit-balance error, OpenAI 429 `insufficient_quota`) is `credits_exhausted`, not a bad key, so it does not call `markBroken`: the run ends `failed` with `failureReason: "model_credits_exhausted"`, `ConnectionStatusPort.markCreditsExhausted(runId)` records the customer's connection for credits (an operator-subscription run records nothing), and no other run is paused. Crossing the per-spawn cap or the model budget mid-run kills the run with status `killed_spend`, settling its real metered cost under the same account+model advisory lock `@fx/spend`'s `settleWith`/`releaseWith` already use, so a concurrent cancel and a concurrent metered kill can't both write a ledger row for the same reservation. `SandboxTarget.resume` reuses the same sandbox name and passes `--resume <sessionId>` for an executor's fix-round retry, falling back to a fresh dispatch on `SandboxNotFoundError`.

**The watchdog (`hookChannel.ts`, `workflows/agentRun.ts`, `#171`/`#174`).** A post-dispatch watchdog — distinct from `startAgentRun`'s own queue-TTL — races a hook wait against a timeout so a dispatched run that never resumes its hook is not stuck forever. `hookChannel.ts`'s `HookWaitPort`/`HookResumeSink` are a structurally-identical pair to `targets/sandboxTarget.ts`'s own `HookResumePort`, kept in a separate file specifically so `workflows/agentRun.ts` never has to import sandbox internals (`test/importBoundary.test.ts` enforces this). `workflows/agentRun.ts`'s `agentRunWorkflow` is now a real `"use workflow"` entrypoint (the stable `workflow` npm package, `#174`) whose dispatch/hook-wait/timeout/cancel/finalize steps are each a `"use step"` wrapper over the already-tested logic above, and the watchdog leg races a real durable `sleep()` instead of an injected `setTimeout`. `hookWaitStep` still wraps `hookChannel.ts`'s in-memory `HookWaitPort`, not a real Workflow `createHook()`/`resumeHook()` pair, and nothing calls `agentRunWorkflow` from a deployed endpoint yet — both are named as follow-on work in the file's own header.

**The run-funding seam (`funding.ts`, `#171`).** Every spend/key call `SandboxTarget` makes resolves its payer account through `resolvePayer` (default: `defaultResolvePayer`) rather than assuming the run's own account: `{ kind: "self" }` (or no `funding` at all) resolves to `run.accountId`; `{ kind: "claim" }` throws `UnsupportedFundingError` unconditionally, since the claim-funded-run feature this seam anticipates is not built. The `agent_runs`/`run_events` writes themselves always use the run's own account regardless of funding.

## Security notes

See `../security.md` for the platform-wide model. Package-specific points: `packages/runner/src/sandboxEnv.ts`'s `buildSandboxEnv` takes no ambient input (no `process.env`, no credential object) and returns only two placeholder values (`ANTHROPIC_API_KEY=""`, `ANTHROPIC_AUTH_TOKEN="brokered-at-firewall"`); `isForbiddenSandboxEnvName` fails closed on any candidate name that isn't even a well-formed env-var identifier (`^[A-Za-z_][A-Za-z0-9_]*$`, catching a leading/trailing space or a hyphen) before testing whether it otherwise matches any other var name shaped like a credential (`FORBIDDEN_ENV_NAME_PATTERN`, which also now matches `PEM` at a name boundary on both sides — e.g. `APP_PEM_FILE`, `PEM_DIR` — not only as a trailing segment). The GitHub forward host that reaches the sandbox's firewall rule is resolved and address-checked by `@fx/net-guard` (see "How it works" above) before a policy is ever built, so a forward host that resolves to a loopback/private/link-local/metadata/multicast/reserved address is refused rather than allowlisted. `SandboxTarget` (`packages/runner/src/targets/sandboxTarget.ts`) carries several rounds of concurrency fixes from PR #85's later revisions, addressing races between a cancel/timeout and an in-flight `dispatch`: it re-checks the run's durable `pending` status after `createSandbox`, again immediately before `startDetached`, and tracks per-instance bookkeeping (`started`, `cancelRequested`, `stoppedDirectly`) so a cancel that lands on the same instance stops the sandbox directly rather than through a reservation table a competing writer may have already emptied. `cancel`'s `stillOwnsSandbox` check also guards against a stale instance stopping a newer run that has since taken over a persistent (executor) sandbox's shared name.

## Deploy verifier on a local runner: setup and the one-time Chrome smoke

The post-merge deploy verifier (`deploy-verifier`) is a runner job only. A machine serves it when its owner sets three values (`fx-runner config set`, never taken from the cloud): `verify.deploy_argv` (a JSON array: a program and a relative script, never a shell string), `verify.deploy_dir` (the repository checkout the script is looked up in, below which every part is checked with `lstat`) and `verify.test_account` (the account label the machine's Chrome is signed in as). The runner advertises `deploy_order_v1` only while the script passes its checks, and `browser_chrome_v1` only while the daemon's own probe passes: Chrome is running, and the Claude in Chrome extension's native host (`claude --chrome-native-host`) has a live socket in `/tmp/claude-mcp-browser-bridge-<user>/`. The probe cannot read which account a page is signed in as without driving the page, so that is judged from the sign-in evidence the browser job reports. A probe that fails when a browser job is claimed ends the run `runner_setup` with detail `browser_not_connected` ("chrome not connected"), never a pass.

The CLI reaches the extension through `--chrome` (only this role; every other role carries `--no-chrome`); the MCP file stays empty. That attach is unproven until this smoke is run once, by the owner, on the runner machine, with Chrome open and the extension signed in as the test account.

**The smoke must run as a runner job runs, not as the owner's interactive login.** A runner job gets the runner's own credential, passed by `cleanEnv` as `CLAUDE_CODE_OAUTH_TOKEN` (subscription mode; the same token the daemon holds) and nothing else of the owner's login. Reading the installed CLI, Chrome is disabled unless the credential carries the `user:profile`, `user:office` or `user:ccr_inference` scope, and a session made from an environment token or `claude setup-token` has inference scope only. So the owner's interactive `claude` can attach while a runner job cannot. Run the smoke with that token:

1. In a clean shell (so nothing of the interactive login applies), export the runner's token as `CLAUDE_CODE_OAUTH_TOKEN` and run, in an empty directory: `claude -p --chrome --strict-mcp-config --mcp-config <a file holding {"mcpServers":{}}> --setting-sources "" --tools Read,Glob,Grep --allowedTools <the nine browser tools from DEPLOY_VERIFIER_BROWSER_TOOLS> --output-format stream-json --verbose "Open a new tab, go to the staging address, and report the page title."`
2. PASS, and the only result that means a runner job can drive Chrome: the `init` line lists Read, Glob and Grep and the nine browser tools and no Bash, Edit, Write, `javascript_tool`, `form_input`, `file_upload`, `upload_image` or `read_network_requests`; the page title comes back; the tab is in the CLI's own tab group.
3. CHROME UNAVAILABLE TO RUNNER JOBS: any of these with the token set: no browser tool in the `init` line, a message that Chrome needs a different login or scope, or the tool calls failing to attach while Chrome is open and the extension connected. Then the runner's credential cannot serve this role. Stop and report; do not work around it with the interactive login, which is not what a job has. (The probe passing only shows the extension is connected, not that the CLI will use it.)
4. With Chrome closed, the same command (with the token) must fail to attach, and `fx-runner run` stops advertising `browser_chrome_v1` at its next hello.
5. If `--tools` refuses the run, or the `init` line shows a tool outside that list, stop and report: the attach or the flag handling differs from what the runner assumes.

### Which kind of fix round a job is

`StartAgentRunInput` and `ExecutionRun` carry an optional `fixRoundKind` (`packages/runner/src/startAgentRun.ts`, `packages/runner/src/executionTarget.ts`), set only by the cloud's own start of a fix round and never taken from a runner (#926). The job issuer (`packages/runner/src/targets/jobIssuer.ts`) signs it into the job as `fix_round_kind` only for an executor job that continues a branch, is not a conflict round and carries a check; any other start is signed without the key, so the runner runs its check. `packages/worker/src/checkFix.ts` sets `check_fix` (the round answers a failed check) and `packages/worker/src/advance.ts` sets `review_fix` for a review or person round, but not for a conflict round and not for a round a confirmed replace started. The issuer holds such a job for a runner at `FIX_ROUND_KIND_JOB_MIN_PROTOCOL` (17) or later (`packages/runner-protocol/src/messages.ts`). `packages/runner/test/jobIssuerFixRoundKind.pg.test.ts` covers the signing rule.

### Test files a check-fix round may add to its scope (#976)

A check-fix round's start (`packages/worker/src/checkFix.ts`) may pass `scopeExtra` on its `StartAgentRunInput` (`packages/runner/src/startAgentRun.ts`, `ExecutionRun` in `packages/runner/src/executionTarget.ts`): the failed test files the cloud counted as inside the change, read from the failed run's stored check summary, plus the files an earlier check-fix round of the same chain was given. The job issuer (`packages/runner/src/targets/jobIssuer.ts`) applies it only to a job that is itself a `check_fix` round and only on top of a Spec scope that was read. It re-tests every path with `checkFixScopeExtra` (`packages/runner-protocol/src/acceptanceScope.ts`): a plain repository-relative file of test-file shape that the Spec's list does not already hold, at most `CHECK_FIX_SCOPE_EXTRA_MAX` (20). Anything else is dropped without refusing the job. The cloud reads the summary's header lines only above the `CHECK_HEADER_END` line, which the runner writes after its header (`packages/fx-runner/src/daemon/checkStep.ts`), and only when the run's runner is at `CHECK_HEADER_END_MIN_PROTOCOL` (19) or later; `CURRENT_PROTOCOL_VERSION` in `packages/runner-protocol/src/messages.ts` is 22. `widenForCheckFix` in `packages/runner-cloud/src/done.ts` holds the pull request to the Spec's list plus exactly those files.

### The engine bridge on the runner (#998, #1002, #1010, #1023, #1036, #1044, #1100, #1107)

The engine bridge connects the autonomous team a person runs on their own machine to the workspace's Team app. It is off unless two things hold: the runner's hello lists the `engine_bridge_v1` capability (the fifteenth in `RUNNER_CAPABILITIES`, `packages/runner-protocol/src/job.ts`) and speaks protocol 20 or later (`ENGINE_BRIDGE_MIN_PROTOCOL`). `HelloMessage` refuses a hello that lists the capability below that version, and `engineBridgeAllowed` in `packages/runner-protocol/src/messages.ts` is the one predicate a route uses. When a cloud refuses a hello, the client drops `browser_playwright_v1`, `browser_chrome_v1` and `deploy_order_v1` first and then this capability, so a cloud without it keeps the capabilities it does know (`packages/fx-runner/src/daemon/client.ts`).

A person turns it on per repo with `fx-runner engine-bridge enable --repo <owner/name> [--repo-root <dir>] [--state-dir <dir>]`, and off with `disable [--repo <owner/name>]`; `status` prints what the running daemon last said, with no event content and no network call (`packages/fx-runner/src/commands/engineBridge.ts`). `enable` asks the cloud which repos this runner is paired with and refuses (exit 2, with a fixed reason) a repo not on that list, an engine state directory another bridged repo already uses, or a repo root with no readable engine version (`engine/manifest.json`, or `.autonomous-team/engine-install.json` in a project that has the engine installed, #1143). With only `--repo` it finds the engine's checkout itself (`packages/fx-runner/src/engineBridge/discover.ts`, #1100). It searches the home directory's `code`, `src`, `projects`, `work` and `dev` folders, then the current directory, the absolute, colon-separated roots in `FX_RUNNER_SEARCH_ROOTS` (`bin/fx-runner.mjs` looks that variable up by name; a root that is not an absolute directory is ignored and counted in the output) and, last, the home directory itself. It never searches the runner's own state directory. The scan goes at most 4 directories deep, stops after 5 seconds or 20000 entries, never follows a link, skips `node_modules`, `.cache`, `.git`, `target` and `dist`, and makes no network call. A clone counts when its `.git/config` names the repo on GitHub and it has a usable `.autonomous-team/project.json`; a clone that is not yours, or that group or others can write to, is skipped and named so the person can run `chmod go-w` on it. Exactly one match is taken. Anything else is a refusal that writes nothing, with a fixed reason: `checkout_not_found`, `checkout_layout_unexpected` (a clone with no usable project file), `checkout_ambiguous` (the message lists the clones and asks for `--repo-root`) or `checkout_incomplete` (the scan hit its time or entry limit with one match, and a second may lie past the limit; run again with `--repo-root`, #1107). The state directory is `--state-dir`, else the project file's `state_dir`, else `$HOME/.<project_name>-state`, else `AUTONOMOUS_TEAM_STATE_DIR`; one taken from the project file must exist and be readable by this user, because the runner never creates it (`state_dir_missing`, `state_dir_unreadable`). A `--repo-root` given by hand skips the scan but still takes the state directory from its project file. When that check itself fails, the message now says what went wrong in words and what to do next: the HTTP status and short error code, or a short network code, never the cloud's own text (#1023). `enable` also prints the checkout and state directory it chose, and `enable` and `status` print which state directory the bridge will read and where that choice came from (`--state-dir`, the checkout's project file, `AUTONOMOUS_TEAM_STATE_DIR`, or the engine's shared default, since `--repo-root` never picks it), and warn when there is no `engine-events.jsonl` there yet, because nothing uploads until the directory matches the one the engine writes to (#1077). A running `fx-runner run` picks the settings file up within seconds and starts, per repo (`packages/fx-runner/src/engineBridge/daemon.ts`):

- an upload loop that tails the engine's events file and the engine host's own events file beside it (`engine-host-events.jsonl`, written by `engineHost/hostFeeds.ts`; #1044), sends batches in order (at most 100 events, requests of at most 256 KiB) and moves each file's cursor only past what the cloud accepted (`loop.ts`). Each file keeps its own cursor (`<repo id>.cursor.json` for the engine's, `<repo id>.host.cursor.json` for the host's), a file the tail refuses or that does not exist yet adds nothing and never stops the other, and the two are merged by event time into one stream with one request per engine instance. An engine instance id belongs to the file it first appears in: a line in the other file that names it is dropped as a schema drop, so one file cannot put events into the other's session (`createBridgeTails` in `daemon.ts`, `tail.ts`). When a batch holds nothing but "alive" events from both sources, the engine's go alone and the host's wait for the next batch. Events other than asks wait up to 60 seconds to go out together (`UNWATCHED_COALESCE_MS`); an ask, its clearing and the halt answer go out at once (`URGENT_KINDS`). When the cloud has heard nothing from the loop for 5 minutes (`HEARTBEAT_MS`) it sends a `bridge_heartbeat`, and a batch of nothing but "alive" events waits for that moment (#1036). While the cloud's switch for the repo is off, the loop waits 5 minutes (`OFF_RETRY_S`) between tries; once a second it also compares the wake epoch the runner already holds, and a change ends the wait at once, so ticking the repo in settings does not wait out the 5 minutes. The look is a local read, not a request, and a wake that finds the switch still off costs one upload try and a new 5 minutes (`OFF_WAKE_CHECK_MS`, `sleepOff` in `loop.ts`, #1050);
- a command puller that fetches the signed engine commands for this runner, judges each (signature, runner, repo, operate switch, expiry, sequence), acks a refusal with a closed reason, and hands valid ones to the engine through an inbox directory in the engine's state directory (`commands.ts`, `inbox.ts`). It pulls at start, when the runner's wake epoch moves, and as a safety net every 10 minutes (`SAFETY_PULL_MS`), or every 20 seconds while no wake answer has ever been seen (`NO_WAKE_PULL_MS`); every 5 seconds it looks locally for outcomes the engine wrote and sends their acks (`ACK_CHECK_MS`, #1036). A halt epoch above the local one runs the kill path before any command is written, and the start-like commands (`start_day`, `resume_loop`, `request_spawn`, `set_dial`) are refused while the repo is halted;
- a dial ceiling keeper that writes a small file in the engine's state directory from the cloud's answer (`ceiling.ts`, #1002). It lives 15 minutes and is rewritten every 5. When a fetch fails nothing new is written, the old file runs out, and the engine then reads ceiling 1 for the spawn class and the two merge classes (`agent.spawn`, `merge.standard`, `merge.fast-path`); `engine_spec_ready` sets no ceiling. A halted repo is written at the strictest ceiling.

One decide socket serves the machine (`decideSocket.ts`): a local Unix socket, mode 0600, that forwards the engine's decision requests to the cloud in the runner's own signed request, and only for repos this runner runs. The socket itself refuses (`operate_off`) only when the answer it is handed is `false` (`packages/fx-runner/src/engineBridge/decideSocket.ts`), but the daemon hands it `true` only after a pull has said operate is on, so before the first pull a request is refused too (`packages/fx-runner/src/engineBridge/daemon.ts`). The cloud signs the commands with the job-signing key through `signEngineCommand` on `JobSigner` (`packages/runner/src/targets/jobIssuer.ts`). Every log line of the bridge is fixed text.

**The bridge status line.** The running daemon rewrites `engine-bridge-status.json` in the runner's state directory at least once a minute (`STATUS_WRITE_MS`). `fx-runner engine-bridge status` reads it and prints, when it is no more than 180 seconds old, `Engine bridge: reported N s ago; hello kept the capability` (or `hello not answered yet`) `; decide socket serving` (or `off`, or `unavailable`). A line per enabled repo follows: the upload state, the last acked sequence number, the last success time and the command pull's state, or `waiting` or `refused` with a closed reason when the repo's loops are not up. When the file is older or missing it prints `Engine bridge: the runner is not reporting (is fx-runner run going?). Repos enabled:` and then each repo as `not running`; with no repo enabled it prints how to enable one; a damaged settings file exits 1 (`packages/fx-runner/src/commands/engineBridge.ts`, `packages/fx-runner/src/engineBridge/daemon.ts`). The cloud's list of repos this runner may bridge must be no older than 25 minutes (`ALLOWED_MAX_AGE_MS`) for a repo to start or keep running; its own pulls renew it (#1036).

### The engine host: the hosted Team Lead (#997, #1009, #1011)

`fx-runner engine-host start | stop | status | resume` runs the engine's Team Lead without a terminal session. It is a second thing a person starts on the same machine, separate from `fx-runner run`; the bridge above carries its commands, the host does the work (`packages/fx-runner/src/commands/engineHost.ts`).

- **`start`** runs the supervisor in the foreground until it ends (Ctrl-C, SIGTERM or the terminal closing end it cleanly). It needs a runnable Claude CLI, found the way the job runner finds it and checked the way a job's is, else it says `no runnable claude CLI was found; run fx-runner doctor`. It prints a fixed sentence and exits 1 when it refuses: the bridge is not enabled for the repo, operate is off, the engine is halted, no systemd user scope can be used to prove a kill, the bridge's local files cannot be read safely, it runs as root, or a host is already running (`REFUSALS`). It exits 0 only after a stop by the person or the machine with no process of the host's tree left.
- **`status`** prints two lines from the two local files and makes no call: `Engine host: recorded (pid N, scope U).` or `no host is recorded on this machine.`, then `Halt: not halted.` or `Halt: halted` with `by a local stop` when it was one, and the epoch.
- **`stop`** ends the host now, with no cloud call, through the same kill path a cloud halt uses (`packages/fx-runner/src/engineBridge/halt.ts`): it writes `engine-halt.json` first, signals the host's process group and, on Linux, kills its systemd scope, then says what it could prove. It exits 1 if a process of the tree is still alive or the halt file could not be written. **`resume`** lifts a local stop and starts nothing; a halt set from the workspace answers that only the workspace can clear it, and exits 1.
- **The bridge state it needs.** The supervisor reads `engine-bridge-state.json` in the engine's state directory: the repo's id and checkout, whether the bridge and operate are on, and when the file was written. The bridge daemon is the only writer. It rewrites the file (0600, through a temp file and a rename, never over a link) after each pull the cloud actually answered, with operate on only when that pull said so, and never from a guess. A file older than 25 minutes (`BRIDGE_STATE_MAX_AGE_MS`, the same age as the cloud's repo list may be), or stamped more than a minute ahead, counts as no file, so the host does not start or stops. The daemon removes it when a repo's bridge stops and when a pull asked for a halt the kill path could not complete, so a halt that did not finish never leaves "operate on" behind. `fx-runner engine-bridge disable` removes it too, so the host does not keep reading "bridge on" while the daemon is down; if it cannot, it says so in one fixed line and the file ages out. A shape other than exactly these fields is refused, and the host does not start (`packages/fx-runner/src/engineHost/hostFiles.ts`, `packages/fx-runner/src/engineBridge/daemon.ts`, `packages/fx-runner/src/commands/engineBridge.ts`, #1047).
- **The process.** One headless Claude CLI run in stream-json mode, started in its own process group inside a `systemd-run --user --scope` unit, working in the repo's checkout, with stdin open for the whole session. A crash restarts it with `--resume <session id>` after 1, 2 and then 5 minutes; a sixth crash within an hour stops it for good (`crash_loop`) until the person starts it again. The stream goes to a local log (`engine-host.log`, rotated at 20 MB, never uploaded). `engine-host.json` records the pid, the scope and a heartbeat rewritten every 15 seconds, which the engine's reader trusts for 60 (`packages/fx-runner/src/engineHost/supervisor.ts`). The trust rules are in [the security model](../security.md#engine-bridge).
- **Ticks (#1009).** The Team Lead gets one fixed message at a time, a tick, and does one turn of work per message. The kinds are `loop` (every N minutes), `checkin` (one per entry of the engine config's `cloud_bridge.ticks[]`, each `{name, every_min}` with 5 to 1440 minutes, at most 50), `start_day` (once a day at a local `HH:MM`), `command` (a cloud command the engine's reader handed over) and, since #1011, `reorient`. A tick is sent only after the previous turn's result; a second tick of a kind already queued is dropped and counted; a turn with no result in 30 minutes ends its tick as an error. `pause_loop` stops `loop` and `checkin` ticks and `resume_loop` lets them go on. A command is claimed by renaming it into `engine-host-inbox/claimed/`, answered with exactly one outcome file (`applied`, `refused`, `expired` or `not_confirmed`, the last for a spawn or stop that no `agent_started` or `agent_stopped` followed within 10 minutes) and never applied twice, also over a restart (`packages/fx-runner/src/engineHost/ticks.ts`, `packages/fx-runner/src/engineHost/hostInbox.ts`).
- **The schedule is the person's own.** `fx-runner config set engine-host.loop-minutes <5-60>` (15 when unset) and `fx-runner config set engine-host.start-day-at <HH:MM>` (none when unset) are kept in the runner's settings, `config unset` clears either, and the host reads them again at every 5-second poll (`packages/fx-runner/src/runnerSettings.ts`, `packages/fx-runner/src/engineHost/hostConfig.ts`). They are written only by `config set` and `config unset`.
- **Continuity (#1011).** The session id the host's first output reports is saved in `engine-host-session.json` (a uuid, 0600, written through a temp file), so a supervisor started after a runner crash or a reboot resumes the same conversation. A resume that fails, meaning the host exits within 30 seconds of launch before printing anything and before being sent a message, drops the saved id, and the next start is a fresh session. When the stream reports that the host's context was compacted, the next tick is a `reorient` message, sent before queued ticks and even while paused. An ask the host already answered is remembered in `engine-host-answered.json` for 7 days, so a second `answer_ask` for it is refused `already_answered` (`packages/fx-runner/src/engineHost/session.ts`, `packages/fx-runner/src/engineHost/answered.ts`).
- **Its own events.** `host_started`, `host_stopped`, `host_heartbeat`, `compaction_detected`, `tick_started` and `tick_ended` are written to `engine-host-events.jsonl` in the engine event shape and rotated at 1 MiB (`packages/fx-runner/src/engineHost/hostFeeds.ts`). The bridge's upload loop tails this file beside `engine-events.jsonl`, each with its own cursor, so the host's events reach the cloud (`packages/fx-runner/src/engineBridge/daemon.ts`, #1044).

### Registering a machine: where the code comes from (#1060)

`fx-runner register` takes the code (`fxrr_`) or provisioning token (`fxrp_`) only from standard input (`--code-stdin`) or from a file (`--code-file <path>`: a regular file you own, no access for group or others, opened without following a link). `--code <value>` is refused with exit code 2 and a message that names the two safe options and never echoes the value, because a value on the command line shows in the process list. Giving both safe options at once is refused too (`packages/fx-runner/src/cli.ts`, `packages/fx-runner/src/codeSource.ts`).

### The microVM engine setting, its limits and the doctor line (#1067)

Nothing in the runner starts a microVM yet. What exists is the configuration and the checks a VM engine will sit behind (`packages/fx-runner/src/vm/limits.ts`, `packages/fx-runner/src/runnerSettings.ts`):

- **The setting.** `fx-runner config set sandbox_engine os_sandbox|microvm` (`config unset` clears it). Absent means `os_sandbox`. A stored value that is neither is not read as `os_sandbox`: the runner claims nothing and `doctor` fails it.
- **The limits.** In `microvm` mode five values must all be set, and none has a default: `microvm.max_vms` (1 to 64), `microvm.max_vcpus` (1 to 256), `microvm.max_memory_mb` (per VM, 256 to 4194304), `microvm.snapshot_dir` (an absolute path written plainly: no `.` or `..` part, no trailing slash) and `microvm.snapshot_quota_bytes`. A value out of range is refused when set, and one stored out of range counts as missing. With any of them missing the runner stops claiming, checked again at every claim (`vmLimitsBlock` in `packages/fx-runner/src/commands/run.ts`). `os_sandbox` ignores them.
- **The doctor line.** `fx-runner doctor` always prints `INFO  sandbox_engine: <line>`, one of a closed set: `microvm`; `os_sandbox (no KVM)`; `os_sandbox (vm helper not installed)`; `os_sandbox (vm state unreadable)`; `os_sandbox (microvm not enabled)`; `os_sandbox (microvm limits missing)`; or, on macOS, `macOS: VM mode not available in this version`. `microvm` appears only when the setting asks for it, `/dev/kvm` and the helper's socket are both there and all five limits are set. A fact the runner cannot read is `unreadable`, never present. When the setting is `microvm`, doctor also fails (and the runner does not fall back to `os_sandbox`) when the engine line is anything but `microvm`, when a limit is missing, when `max_memory_mb` is over the host's total memory or `max_vcpus` over its cores, or when the available memory cannot be read; it prints the limits and the host's available memory when they pass. The machine's answers come from `packages/fx-runner/scripts/vm-facts.mjs`, the helper's socket defaulting to `/run/fx-vmhelper/helper.sock`.
- **The admission guard.** `admitVm` in `limits.ts` is a pure function that says whether one more VM may start, and it refuses rather than queues. It counts every running VM at its full configured memory, not its resident size, and needs the new VM's memory plus 1 GiB of headroom to be available on top of that. It refuses with a closed code: `limits_missing`, `bad_request`, `vm_cap_reached`, `vcpu_cap_exceeded`, `memory_cap_exceeded`, `mem_unreadable` or `mem_low`. Nothing calls it outside its tests yet.
- **The image check (boot facts).** `src/vm/bootFacts.ts` answers what a microVM boots from, and it has no override: no setting, variable or argument skips it. The installed `/opt/fx-vmhelper/template-manifest.json` names the kernel and root-disk digests of the template; exactly one signed release (`vm-<template>-<id12>`) in the verified listing must list both for this architecture, and the agent digest comes from that same release. Every failure is one closed code with a fixed sentence and no digest, path or server text: `image_not_configured` (the build has no trusted root), `image_metadata_expired`, `image_metadata_refused`, `image_not_installed` (the manifest is missing or damaged), `image_not_listed` (the installed image is not in the signed metadata, for instance a withdrawn one), `image_listed_ambiguous`, `image_incomplete` and `arch_unsupported`. A machine with no verified release boots nothing and `Sandboxd.create` ends before any helper call. A verified listing is kept for 60 seconds and a failure is never kept, so a withdrawn release (`tuf-release.mjs release --drop`) stops booting up to a minute later; running VMs are not touched. `fx-runner doctor` prints a `VM image` line from the same function the runner uses, sharing one listing fetch with the `VM binary` line: PASS with the release id and the first 12 digits of each file, FAIL when `sandbox_engine` is `microvm` and WARN otherwise. Nothing updates itself: after a refusal, run `fx-runner vm install`.

### Platforms (#1063, #1065)

The runner supports Linux. macOS is a preview, not yet verified (jobs run in Claude Code's own sandbox). Native Windows and WSL1 are refused at start (`windows_unsupported`, `wsl1_unsupported`). WSL2 is a preview that runs the OS sandbox only (`fx-runner doctor` prints `WSL2: VM mode not supported`) and starts only when every check and live probe passes; until then it is refused by name (`wsl2_unsupported`). WSL2 is recognised by its kernel string or the `WSLInterop` entry in `binfmt_misc`, never by the distribution variable alone. The checks, run at every `run` start before any claim and by `doctor`, are that Windows interop is off, no 9p, drvfs or virtiofs mount reaches the Windows side unguarded, the runner's directories are not under the Windows drives' mount root, and the Windows `PATH` is not appended. Jobs are denied the Windows mounts and the WSL runtime directory, and three probes, each with a control, must run: a job cannot read a Windows drive, cannot start `cmd.exe`, and the probe itself ran. Under mirrored networking (anything but `nat`) a job may not ask for a loopback bind. `packages/fx-runner/README.md` has the full list of check names and the `/etc/wsl.conf` settings.

### The VM helper (`fx-vmhelper`, #986)

`packages/fx-runner/vmhelper/` is the root service behind the runner's Firecracker sandboxes: Go, standard library only, Linux only (`packages/fx-runner/vmhelper/README.md`, which is the full reference). It holds the protocol and the server, the sandbox registry (id allocation, the jail and vsock directories, start-up reaping), the real launcher (`start` runs the pinned jailer, which builds the chroot, puts Firecracker in its own cgroup below the unit's `vms` subtree and drops to the sandbox's uid and gid), template staging with a sha256 check against a root-owned manifest, the vsock directory bind mount, and the Firecracker API calls that boot the VM and ping it over vsock (#1064, #1068, #1072). What the daemon above it does with all this is under "The sandbox daemon" below; `fx-runner run` does not call that daemon yet.

- **Protocol.** One JSON object per line, at most 4096 bytes, one reply per request, verbs `prepare`, `start`, `destroy`, `list`, `snapshot`, `resume` and `snapshot_delete`. A sandbox id matches `^[a-z0-9][a-z0-9-]{0,39}$`, so it can never read as an option. Duplicate keys, `__proto__`, unknown fields, nulls, booleans, arrays and nested objects are refused. A reply is `{"ok":true,"protocol":1,...}` or `{"ok":false,"protocol":1,"code":"<code>"}` with the code from a closed list; no input is echoed, and a refused frame ends the connection.
- **Snapshots (#1081).** `snapshot` pauses a running sandbox, has Firecracker write a full snapshot (device state plus all guest memory), kills the VM and moves the files into the root-owned `snapshot_dir` (`0700` directories of `0600` files that neither the runner nor a sandbox uid can open). `resume` starts a prepared, stopped sandbox from a stored one, after checking it against the sandbox's template, vcpus, memory and the manifest's digests (`snapshot_mismatch` otherwise). A snapshot is as big as the guest's RAM, and the helper keeps no list of them and decides nothing about how many to keep: the daemon does. The runner must remove the stopped VM's `v.sock` before a resume.
- **Who may connect.** Only the process whose uid the kernel reports (`SO_PEERCRED`) as the `runner_uid` of the root-owned config. The socket's file mode and the caller's groups play no part. A frame must complete in 5 seconds, 8 connections are served at once and the ninth gets `too_busy`.
- **Start-up self-check.** Before it reads its config the helper compares `/proc/self/status` with a pinned set: effective and bounding capabilities equal to it, no ambient capabilities, `NoNewPrivs` 1, seccomp in filter mode. Any difference is one fatal line and exit 1. The pinned values, each with its reason, are in `packages/fx-runner/vmhelper/internal/hardening/hardening.json`; the unit generator (Go and TypeScript), the NixOS module, the check and the tests all read that one file.
- **Config.** `runner_uid` and `runner_gid` are the runner's ids, neither 0. The per-sandbox uid and gid ranges start at 100000 or above, never hold 65534 or the runner's own id, and the gid range must not hold the group of the socket directory or the helper's own gid (checked at start).
- **The install plan and the unit (#1083).** `packages/fx-runner/src/vm/installPlan.ts` builds one pure object that says what a VM-mode install puts on a machine: the hardened systemd unit text, the root-owned config with all 15 keys (`CONFIG_KEYS`, pinned by a test to the Go parser's list), and a create list of 13 items that uninstall removes in reverse. The host facts (CPU count, `MemTotal`, the ids already taken, the invoking user) are passed in, so the plan reads no machine and runs no program. `renderUnit` in `packages/fx-runner/src/vm/unitRender.ts` is the TypeScript twin of the Go renderer: it reads `hardening.json` and restates none of it, and a test compares its output with golden unit files the Go renderer wrote. The default limits are `max_vcpus` = the CPU count (at most 64), `max_mem_mb` = three quarters of `MemTotal`, and `max_sandboxes` = that memory divided by the smallest template's RAM, at most 8; the sandbox uid and gid ranges are the first free block from 100000 up. The jail root is `/var/lib/fx-vm` (`0711`) and the snapshot directory `/var/lib/fx-vm-snapshots` (`0700`, root only, outside the jail root); the unit lists the snapshot directory as writable, since `ProtectSystem=strict` would make it read-only. Nothing runs the plan yet: the steps that apply it are separate work. `nix/fx-vmhelper.nix` is the same service as a NixOS module (`services.fx-vmhelper`, with a `snapshotDir` option); it only describes the service, asserts that `snapshotDir` is not the jail root and does not contain it or sit below it, and takes the unit text from `nix/fx-vmhelper-unit.nix` (`nix/tests/module-eval.nix` evaluates it).
- **Tests.** `scripts/check.sh` runs `go vet` and `go test` there whenever `packages/fx-runner` is part of the run, and the Go files are not in the test-file counts on [the status page](../status.md). The ordinary Go tests need no root. The one that launches the real pinned jailer and Firecracker needs it and runs only in `.github/workflows/vmhelper-real-root.yml` (by hand, and on a pull request that changes `packages/fx-runner/vmhelper`), on a throwaway hosted VM.

### The sandbox daemon and the egress relays (#1070, #1075, #1085, #1069, #1073, #1082, #1087)

`packages/fx-runner/src/vm/sandboxd/` is `fx-sandboxd`, the unprivileged half of the microVM engine: named sandboxes (create, get, stop, resume, delete, list), detached commands, file put and get, and snapshot bookkeeping. It refuses to be built as root, and everything privileged goes to the VM helper through its client. `fx-runner run` composes it (`createLiveMicrovm`, with the egress policy port and the microVM sandbox port over it) only when every part is present: the helper client, the egress proxies, the runner's uid, the boot facts, the guest agent runtime, the per-sandbox bindings and the model token's reader. The entry point (`bin/fx-runner.mjs`, through `src/vm/liveParts.ts`) supplies all of them: the boot facts come from the signed release listing and the installed manifest, and the token is read in one function there, as a fresh buffer on each call. A build that lacks any one part reports `microvm_build_unwired` in `fx-runner doctor`, claims nothing, and never runs a job in the OS sandbox instead. `run` then wires the job handler's VM side over the stack (`src/daemon/vmJobDeps.ts`); each job's VM is made for that job's own wall-clock limit and bound with that run's usage gate and relay sinks (a build without that part is not wired, and a VM is refused when none is attached). The claim loop also stops at the VM cap (`vm_cap_reached`), refuses to claim on an API key (`microvm_api_key_unsupported`), and ends the VMs the helper still holds before the first claim (`vm_reap_pending` while one cannot be ended). The engine is chosen once when the runner starts, while the setting is read again at every claim: a setting that says `microvm` while the run did not choose it (an unwired build, machine facts that could not be read at start, or a setting changed while the runner runs) stops claiming locally (`microvm_build_unwired`, or `microvm_restart_needed` for a wired build, which says to restart it). The VM gate asks the machine again at most every five minutes even after a pass, so a helper that dies after start closes it. A settings file that cannot be read stops claiming and is never overwritten: every `config set` or `unset` is refused with a fixed message except `config set sandbox_engine`, which is the way out.

- **Reaching the guest.** The daemon talks to the in-guest agent (`infra/microvm-image/guest/agent.py`, ping, exec, put, get, and `exec_stream` and `kill` where `ping` lists them in `caps`) over Firecracker's vsock proxy. It looks at the vsock directory and `v.sock` through `O_PATH|O_NOFOLLOW` descriptors and connects through its own descriptor table, never through a path a sandbox could re-point; a symlink, or a `v.sock` that is not a socket owned by the runner's user, is refused.
- **Files and teardown.** A file body is at most 256 MiB and goes in 1 MiB pieces; the host refuses a relative path before it reaches the guest. A global teardown destroys every sandbox the daemon prepared, each bounded by its own timeout, and then checks that no Firecracker process is left.
- **Snapshots (#1085).** `stop` on a persistent sandbox snapshots it and `get` with resume restores it. The daemon keeps its own list in a `0600` state file under a `0700` directory (`sandboxd-snapshots.json`), so a restart still finds them. A sandbox keeps one snapshot unless told otherwise (at most 10), and a snapshot expires after 30 days. A snapshot is admitted only when the free space on the snapshot directory covers the guest's RAM plus 4 MiB of device state and the bytes held plus this one fit the `microvm.snapshot_quota_bytes` limit; a refusal names both numbers it compared.
- **Egress (#1069, #1073).** A guest has no network card. Its only way out is vsock, and each VM gets two listeners on host-side sockets in its own vsock directory, so a request is attributed to a sandbox by the socket it arrived on, never by anything the guest sends. The proxy (port 5253) serves `CONNECT host:443` for hosts on the sandbox's policy: the host must be a plain DNS name, every resolved address must be public and none the host's own, and the connect goes to the validated address, so a name that changes its answer cannot rebind between check and use. A host whose policy rewrites the request (a model host with a header, a forwarded host) cannot be tunnelled; the reverse endpoint (port 5254) serves it as plain HTTP from the guest and makes the upstream TLS request itself, with the credentials attached on the host side, so the guest never holds one. It also serves a host the policy lists with no rules (a job's own policy is such a plain list) as itself, with the same address checks and nothing added. The image carries the guest half: `relay.py`, started by `init`, carries `127.0.0.1:5253` to vsock 5253 and `127.0.0.1:80` to vsock 5254, and the guest's hosts file maps the model host and `github.com` to the loopback. A policy shape the proxy cannot read leaves the sandbox with no egress at all.
- **The SDK adapter (#1082).** `createDaemonSdk` (`packages/fx-runner/src/vm/sandboxd/sdkAdapter.ts`) puts the cloud sandbox port's `VercelSandboxSdk` slice on top of the daemon, so `vercelSandboxPort` can run on a microVM unchanged. The slice (`sdkSlice.ts`) is a copy, because this package may import nothing from the cloud runner package; `sdkAdapter.test.ts` assigns the adapter to the real type, so a drift on either side fails `tsc`. The adapter translates and decides nothing the daemon does not: every daemon check still runs, and a refusal reaches the port as the HTTP-shaped error the real SDK throws (`response.status` and a short fixed `json.error.code`). A port name becomes a daemon id of `sb-` and the first 32 hex digits of its SHA-256, and two names that ever hashed alike are refused. It never creates a sandbox without a network policy: it refuses to build without a policy port, nothing runs in a session until the policy is in force, and a sandbox whose policy could not be applied is destroyed (or stopped again, on a wake) before the caller sees it. Everything that changes one sandbox's session runs one at a time per id, in the order asked. A sandbox is stopped when its timeout runs out (`extendTimeout` moves that). Usage reports memory, duration and region; CPU time and egress bytes are left out, never reported as 0.
- **The policy port and the runner's own views (#1087).** `createEgressPolicyPort` (`policyPort.ts`) turns a sandbox's policy into the two listeners above on that sandbox's own vsock directory, using the directory and gid the helper reports for the id. A new policy closes the old listeners first, so there is a gap with no egress and never one where the old policy still answers; if either listener fails to start the other is closed and the sandbox has no egress; a sandbox the helper does not list is refused. `management.ts` builds the runner's inventory source and sandbox lifecycle on the adapter (`daemonInventorySource`, `daemonSandboxLifecycle`), so the claim's `sandboxes` block and the signed stop, delete and reap commands (see below) read and change the same table the port uses. Inventory names are the daemon ids (`sb-...`), never a port name, which can carry branch text; at most 200 rows go out, newest first. Disk bytes and snapshot count are reported as 0 and the snapshot age as null, because the adapter does not measure them yet. A command's refusal is `in_use` for a busy sandbox (HTTP 409) and `failed` for anything else. Nothing builds these in `fx-runner run` yet.

### The clone size watch and the deepening fetch (#1104)

A preview's clone and the conflict round's deepening fetch share one size watch: a repository over `MAX_CLONE_KB` (200 MiB, checkout plus history) is stopped and its checkout removed, and the script exits `CLONE_EXIT_TOO_LARGE` (87), which the port reports as `clone_too_large` (`packages/runner/src/repoClone.ts`, `packages/runner/src/vercelSandboxPort.ts`). The deepening script (`DEEPEN_SCRIPT`, used by `checkoutBranchCommand` in `packages/pipeline/src/review/reviewPrompts.ts`) runs the fetch in its own process group, so an oversize kill reaches the helper processes git starts as well; killing only the parent left them writing into the checkout while it was being removed, and the removal failed. The fetch's group is also killed however the shell ends. The checkout is removed with one retry, and a checkout still on disk after that exits `CLONE_EXIT_NOT_REMOVED` (90) instead of 87, so a leftover directory is never reported as an ordinary "too large". Any non-zero code other than 87 reads as `clone_failed`.

### A fix round under a runner parent (#989)

A runner run can have at most one runner child, because of a database key on runner follow-ups. When an executor fix round ended without a session (a refused push), the next round used to pick that run as its parent and be refused by the key for good. `freeRunnerParent` in `packages/worker/src/advance.ts` now walks to the end of the runner-child chain (at most `RUNNER_CHAIN_HOPS_MAX`, 50 hops) and starts the round under that run; a longer chain is refused as `parent_chain_too_long`, and a unique-key refusal from the database answers `already_running` instead of a dead end.

### Overlap facts on a blocked plane merge (#963, #964)

`overlap_facts_v1` is the fourteenth runner capability (`packages/runner-protocol/src/job.ts`) and gates no role. A runner that kept it, and `ordered_facts_v1`, puts an `overlap_facts` verdict on its plane-merge verify message when its ordering fact names an overlap (`PlaneMergeVerifyMessage` in `packages/runner-protocol/src/messages.ts`; the message is refused if `overlap_facts` comes without an overlap). `computeOverlapFacts` (`packages/fx-runner/src/daemon/conflictFacts.ts`) names the files that both the reviewed head and the private default branch changed since their merge base, and says whether the platform wrote every commit touching them; anything it cannot establish is `unknown`, and it sends paths only, never content. `packages/fx-runner/src/daemon/client.ts` drops the capability, after the two browser capabilities and `deploy_order_v1`, when a cloud refuses it on the hello, so the runner keeps the others.

### Which browser method a deploy verifier job uses

The cloud chooses how each deploy verifier job drives its browser and signs the choice into the job as `browser_method`: `playwright_runner` (the runner's own Playwright browser, driven through the runner-owned `fxverify` MCP server) unless the repository's verify setting `browser_driver` (migration 1007; `playwright` by default, written by an owner or admin of the account only) is `chrome`, which is set only after the smoke above passes (the stage reads it under the repository's tenant when it starts the job). A job that carries `browser_method` is gated at protocol 16 (`BROWSER_METHOD_JOB_MIN_PROTOCOL`): a runner below it is never offered one, whatever browser capability it advertises, because its strict parse would refuse the key and fail its whole claim; update the runner to receive deploy verifier jobs. Each method has its own capability on the runner's hello (`browser_playwright_v1`, `browser_chrome_v1`) and its own tool list, and the signed tool digest covers the list of the job's method. The cloud offers a job only to a runner that lists the capability of its method. The verify row's method is copied from the signed job, never from anything the run reports.

### The runner's own Playwright browser (`playwright_runner`)

A deploy verifier job with the `playwright_runner` method drives a Chromium that the runner starts itself, through the runner-owned `fxverify` MCP server (twelve small tools; none runs a script, reads the network, uploads, downloads or takes an address or selector). It never uses the person's running Chrome or its profile.

**What the machine needs, set once by its owner**

1. A Chrome or Chromium: `fx-runner config set verify.browser.executable <absolute path>`.
2. The app's address: `fx-runner config set verify.browser.base_url <address>` (https, or http on localhost; no credentials, query or fragment). It must be the app's own canonical origin (its `FX_APP_ORIGIN`), not another domain that redirects to it: sign-in lands on the canonical origin, and a session saved for any other address would not be the app's.
3. The test account's label: `fx-runner config set verify.test_account <label>`.
4. The test account's session: `fx-runner verify-login --base-url <address>`, run in a terminal (it waits for you to press Enter after signing in, so it refuses to start when standard input is not a terminal, and ends with a message, never a hang, if input closes first). If the app signed you in at a different https origin than the one you gave, it saves nothing and tells you which one to run again with (`--base-url <that origin>`). A headed browser opens on the app; sign in as the TEST user, then press Enter in the terminal. The browser's storage state is saved to `~/.config/fx-runner/verify/storage-state.json` at mode 0600 (inside the credential floor, so a job's tools cannot read it) and is never printed; the command shows only the date the app's session cookie expires. Only the app's own origin is saved: the cookies of the app's host and the page storage of the app's address. Whatever else the browser held (the identity provider's own sign-in above all) is dropped before anything is written, and nothing is saved if the app's session cookie (`__Host-fx_session`) is not among what is left. The address is saved as `verify.browser.base_url`, and the browser as `verify.browser.executable` when it was found rather than set. `verify.browser.storage_state` may name another file, but it must stay inside `~/.config/fx-runner`. Repeat the sign-in when the probe reports the session expired.
5. The Playwright library: from source it is an ordinary dependency. The single-executable release does not bundle it (it cannot be bundled); it is loaded from a sidecar folder next to the binary, `fx-runner-playwright/node_modules/playwright-core`. The folder is exactly the pinned `playwright-core` (1.63.0, Apache-2.0) with its runtime files and licence files and no browser (Chromium is still `verify.browser.executable`). The loader looks for that folder, and only that folder, and refuses code from anywhere else in two ways (`bin/sidecarLibrary.mjs`). (1) The library entry it resolves must have a real path inside the folder, so a copy of playwright-core itself on `NODE_PATH`, in `~/.node_modules` or in a parent folder is refused. (2) Before anything is loaded it installs a module-resolve fence (`module.registerHooks`) for the life of the process: every module that a file inside the folder asks for must resolve to a file inside the folder, or to a `node:` built-in, otherwise the require throws. This covers the optional `bufferutil` and `utf-8-validate` addons that playwright-core's bundled `ws` tries to load (a copy planted in a parent `node_modules`, on `NODE_PATH` or in `~/.node_modules` is never resolved, so it never runs), and any require made later, lazily. As a second layer the loader also sets `WS_NO_BUFFER_UTIL=1` and `WS_NO_UTF_8_VALIDATE=1`, so `ws` does not look for those addons at all. Not covered: a writer of the folder who is the same user as the runner can also replace the binary, so that case is out of scope for the digest and the fence alike. An installed runner is the built single executable, not the source tree, so the folder has to sit beside that binary (an installed runner gets it from the next update, or from `sidecar-cli.mjs install` below). The release build bakes the digest of the whole folder into the executable, and the loader also refuses a folder whose files, names or links differ from it (an edited, added or removed file, a second library, a link): the probe then reports `playwright_missing`, as it does when the folder is absent.

**How the sidecar ships and updates.** `scripts/build-sea.mjs` writes the folder beside the binary in its output folder, plus `fx-runner-playwright.fxsc`, one packed archive of it (the same bytes on every platform), and lists the archive in `release-manifest.json`. The release signs it as the target `v<version>/fx-runner-playwright.fxsc` next to the four binaries, so the signed metadata covers its length and SHA-256. The updater fetches it right after the binary, checks the hash again, unpacks it into the same staging directory (every file against the archive's header and the whole tree against its digest; only plain files under `node_modules/playwright-core`), and installs binary and folder with the one rename; a listed sidecar that fails any check refuses the whole update and nothing is changed. A release that lists none installs as before. A fresh `install.sh` install has only the binary: the next `fx-runner update` (and the daemon's automatic check) lays the sidecar down for the version in use, swapping it in atomically with the old folder put back if that fails. A machine whose runner is built from source with `build-sea.mjs` gets the folder in its `--out-dir`; a binary kept elsewhere gets it with `node packages/fx-runner/scripts/sidecar-cli.mjs install --binary-dir <folder of the binary> [--digest <hex>]` (with `--digest`, a library that is not the one the binary was built with fails the install loudly), which can be checked with `... verify --binary-dir <folder>`. A single executable built before this change has no digest baked in and never trusts a sidecar folder: rebuild it once with `build-sea.mjs` (or install a release built with it) before a sidecar works; `sidecar-cli.mjs install --binary-dir` is for a binary built by this `build-sea.mjs` and kept elsewhere. Running the runner from source needs nothing: the library is an ordinary dependency.

**When the capability is advertised.** `fx-runner run` lists `browser_playwright_v1` on its hello only while the daemon's probe passes: test account and base URL set; the executable present, runnable and named like Chrome or Chromium; the library loadable; the storage-state file a plain file, mode 0600, owned by the runner's user, inside the credential floor, holding the app's own signed session cookie (`__Host-fx_session`, the name `packages/core/src/auth/session.ts` sets; another cookie of the host, such as an analytics one, never counts) for the app's host that has not expired, and nothing of any other origin (a cookie of another host or page storage of another origin ends the probe with `storage_state_foreign`; the server refuses such a file too, before the browser starts). A claim for a playwright job re-checks it; on failure the job ends `runner_setup` with `browser_not_connected` and the terminal names the probe reason (for example `storage_state_expired`).

**How a job runs.** The job's MCP file holds one entry, `fxverify`, started by the Claude CLI as this program's own `verify-browser-server` command with the job directory, address, executable and storage-state path as arguments. Every other role and method gets an empty MCP file; `--strict-mcp-config` stays on, and the command line carries `--no-chrome`, never `--chrome`. The job's tool list, settings, take-over command and prompt all use the signed method. The answer is the `answer.json` the server wrote (shape-checked and grounded in what the page showed); the model's final text is ignored for this method, and no valid file means no answer (unverified). The production wiring never accepts invalid certificates.

**Who the session is signed in as.** When the answer is accepted, the server itself makes one read-only `GET /api/cloud/auth/me` on the app's origin through the browser context (so it carries the saved session), without following a redirect and with a size cap, and writes the `username` it returns (the signed-in user's GitHub login) as the top-level `signed_in_as` of `answer.json`. A lookup that fails, redirects, is too large or does not hold a plain 1 to 100 character login leaves `signed_in_as` out. When a browser was started, the server then writes `signed_in_as_unavailable` (the one word `sign_in_expired`) in its place, and the cloud parks the row to wait for a new sign-in instead of failing it (#947, `packages/fx-runner/src/verifyBrowser/server.ts`); with no browser started the field is left out and the cloud fails the row closed as before. The model cannot set either: a `signed_in_as` or `signed_in_as_unavailable` in its own answer is refused (`packages/fx-runner/src/verifyBrowser/ground.ts`). The daemon reads `answer.json` through a handle opened without following a link, checks that it is a plain file of the runner's own user at mode 0600, and removes it afterwards.

**How old the saved session is (protocol 18, #947).** `fx-runner verify-login` writes a small sidecar next to the saved sign-in with two dates only: when it was saved and when the app's session cookie ends (`packages/fx-runner/src/commands/verifyLogin.ts`). `packages/fx-runner/src/daemon/signInState.ts` turns them into one word: `expired` once the earlier of the cookie's end and 22 hours after saving has passed, `expiring_soon` under two hours before that, otherwise `ok`, and `missing` when a verify address is set but no plain saved file is there. A sign-in saved before the sidecar existed is dated by the file's modification time. The daemon puts the word on its claim as `verify_sign_in` only when its protocol version is 18 or later (`VERIFY_SIGN_IN_MIN_PROTOCOL` in `packages/runner-protocol/src/messages.ts`, `packages/fx-runner/src/daemon/client.ts`); with no verify address set it says nothing. Nothing from inside the saved file is read, logged or sent.

**Removing the saved session (the way back).** `fx-runner verify-login --forget` deletes the storage-state file (a link is removed itself, never followed). `fx-runner config unset verify.browser.storage_state`, `verify.browser.base_url` and `verify.browser.executable` leave the file in place; to remove the session, run `--forget` first. Without the file the probe reports `storage_state_missing`, and the hello drops the capability.

**Where the server runs.** The server is started by the CLI as a stdio child. A test (`test/verifyBrowser/entry.real.test.ts`) starts the entry the way the engine's MCP file spells it, without the CLI, and shows it runs in the same mount, network, user and pid namespaces as its starter, with Chromium beside it, and with no token in its environment. Whether the real CLI wraps its MCP children in a sandbox of its own cannot be shown without running it, so it is part of the smoke below.

**Owner smoke, once, on the runner machine** (uses the real CLI and the real app; nothing here is automated):

1. Run steps 1 to 4 above, then `fx-runner run`; the hello must list `browser_playwright_v1` (with Chrome closed, `browser_chrome_v1` is not listed and this one still is).
2. Run one deploy check on the staging app. In the job's transcript: the `init` line lists Read, Glob, Grep and the twelve `mcp__fxverify__*` tools, no Bash, Edit, Write or Chrome tool; the first snapshot shows the app signed in as the test account.
3. During the job, `ls -l /proc/<pid of the fx-runner verify-browser-server process>/ns/net` should match the runner's own; if it differs, the CLI sandboxes its MCP children and Chromium needs checking there. Report either result.
4. Let the session expire (or move the storage-state file aside): the next claim must end `runner_setup` and the hello must drop the capability.
5. After a successful job, `answer.json` is gone and the run's done payload carries `signed_in_as` equal to the test account's GitHub login. Then run `fx-runner verify-login --forget` and confirm the file is deleted.

## Known gaps

- `fx-runner setup --cloud-url <url>` and a `register` run with no code link a machine by a typed code (`packages/fx-runner/src/commands/setup.ts`, `packages/fx-runner/src/deviceRegister.ts`). `setup` refuses a machine that already holds a registration, prints the failed `doctor` checks without stopping on them, installs and starts the per-user service, and on a machine with KVM and no VM helper ends with `sudo fx-runner vm install`.
- The microVM engine is composed by `run` (`src/vm/liveParts.ts`, `src/daemon/vmJobDeps.ts`); a whole job through `run` in a real VM is not yet proven. The guest's events and near-limit warnings reach the run's usage gate and relay, the VM cap gates claiming, and the helper's leftover VMs are ended at start; the reap does not look again after start, so a VM that outlives a job later is only counted and retried through the job lifecycle's own table. Built: boot facts from the installed template and the signed release (`src/vm/bootFacts.ts`), the working copy going into the guest and the agent's commits coming back out as a bundle the host checks (`src/vm/workspace/`), and the approved check running in a fresh VM (`src/vm/workspace/guestCheck.ts`).
- No production `SandboxPort` implementation exists in this package — only the interface and the fake (`packages/runner/src/sandboxPort.ts`'s own header, `packages/runner/src/fakeSandbox.ts`).
- `C15`/`C26` (`#171`'s own deferred scope): no real `@vercel/sandbox`-backed `SandboxPort` and no production composition root that actually calls `startAgentRun`/`agentRunWorkflow` from a deployed endpoint yet.
- `workflows/agentRun.ts`'s `agentRunWorkflow` (`#174`) is real Workflow-SDK code, but its `hookWaitStep` still wraps `hookChannel.ts`'s in-memory `HookWaitPort` rather than a real `createHook()`/`resumeHook()` pair, and its `pool`/`registry`/`hookWait` constructor-style parameters are not yet the serializable-only entrypoint a real composition root would need (both named as H14 follow-on work in the file's own header).
- `funding.ts`'s claim-funded run support (`{ kind: "claim" }`) fails closed with `UnsupportedFundingError` — the feature it anticipates (D#70) is not built.
- `SandboxTarget.admit` (`packages/runner/src/targets/sandboxTarget.ts`) calls `@fx/spend`'s `reserve` in its own transaction rather than the caller's, so the spend reservation and the `agent_runs` insert do not commit atomically yet; the `client` parameter is accepted but unused, documented as a seam for a future shared-transaction version of `reserve`.
- `INSTALL_PHASE_REGISTRY_ALLOWLIST` hosts are reached directly rather than through the GitHub proxy, and accept publishes as well as installs during the install phase — noted as a `TODO` in `packages/runner/src/networkPolicy.ts` pending a real firewall component.
- `loadGithubForwardConfig` (`packages/runner/src/githubForwardConfig.ts`) is now called in production (`#140`) — once, at module scope, in the gh-proxy route (`apps/web/app/api/gh-proxy/[...path]/route.ts`), for that route's own OIDC-audience/host-binding checks (`githubProxyForwardUrl`, `#160`). It is still not wired into `SandboxTarget`'s `deps.githubForward` / `buildFirewallPolicy`'s `deps.githubForward` — those still take a caller-injected `GithubForwardConfig`, and no production composition root exists yet to supply a real one (see the `C15`/`C26` gap above).

**Sandbox inventory and host limits (protocol 21, `SANDBOX_INVENTORY_MIN_PROTOCOL`).** A runner may put an optional, closed `sandboxes` block on an ordinary claim (never on a status poll): at most 200 rows, each with `name` (the VM helper's sandbox id pattern), `state` (`creating`, `running`, `stopped`, `snapshotted`, `error`), `created_at`, `last_used_at`, `disk_bytes`, `snapshot_count` and `snapshot_age_s`, and nothing else. `createInventoryReporter` (`packages/fx-runner/src/daemon/sandboxInventory.ts`) sends it only when the hash of the list changed, or at least every 10 minutes, and counts a send once the cloud answered 200; the default `InventorySource` lists nothing until the VM helper provides one. The cloud stores the list whole through `runner_sandboxes_record` (migration 1040) and keeps the time of the last report per runner in `runner_sandbox_reports`; the definer refuses unknown keys, a runner whose hello declared less than 21, more than 200 rows and repeated names. The hello facts may also carry `max_vms`, `max_vcpus`, `max_memory_mb` and `bootable_templates`, written by `runner_sandbox_facts_record` onto the runner's facts row. All of it is a claim by a semi-trusted machine, for routing and display: `packages/runner-cloud/test/sandboxInventory.imports.test.ts` fails when any file outside a short list names these tables or fields, and when a request-verification, signing, ticket or grant path does.

**Sandbox commands (protocol 21, capability `sandbox_commands_v1`; migration 1041).** An owner or admin queues one of `stop_sandbox`, `delete_sandbox` (both with a `name` in the sandbox id pattern) or `reap_sandboxes` (no name) for one runner (`enqueueSandboxCommand`; the row in `sandbox_commands` is also the record of who asked). The claim reply of a runner whose latest hello listed the capability at protocol 21 or later carries up to five signed commands in `sandbox_commands`: `{ purpose: "sandbox_command_v1", runner_id, kind, name?, nonce, exp }` under the job-signing key, so a signature over a job or an engine command never verifies as one. The runner (`createSandboxCommandReceiver`) checks the signature, its own id, the expiry (and a life of at most 10 minutes), the name pattern and that the nonce is unused (the nonces seen are kept with their `exp` in `sandbox-commands-state.json`, 0600, so a restart does not forget them; only when that file was missing at start (nothing to check a nonce against), a command whose `exp` is before the process start plus 10 minutes is refused, so a first start takes no command for its first five minutes; with a clean file a fresh command is taken at once, and a file that is a link, open to others or malformed makes the runner take none) before it calls `SandboxLifecycle`; a command that fails any check is dropped without an ack. Asking again for a request nobody claimed in time retires the stale row first (a person may move a pending row past its life to `expired`) and queues a fresh command. The default lifecycle refuses everything (`unsupported`) until the VM helper's daemon backs it. Acks (`sandbox_acks`, at most 20) ride on the next ordinary claim and count as sent once the cloud answered 200. The run-job schema is not widened.

**Machine onboarding shapes (protocol 22, `MACHINE_ONBOARDING_MIN_PROTOCOL`; #1078).** The protocol package now defines the shapes the cloud will use to set a project up on a person's own machine; nothing in `packages/fx-runner` acts on them yet. Six capabilities gate the work, each offered only to a runner whose latest hello lists it: `device_register_v1`, `project_setup_v1`, `survey_v1`, `engine_session_v1`, `machine_login_v1` and `repo_token_refresh_v1`. A signed machine job (`packages/runner-protocol/src/machineJobs.ts`) is one of `project_setup`, `engine_update`, `engine_session_start`, `engine_session_stop`, `engine_session_delete` and `project_remove`; it is bound to one runner and one repo, lives at most 30 minutes, has closed arguments, and takes an engine tarball only from `codeload.github.com` or `github.com`. Two signed machine commands, `claude_login_start` and `claude_login_code`, carry the Claude sign-in link (`machineCommands.ts`, at most 10 minutes, one request id each, a URL only on `claude.ai` or `console.anthropic.com`). The engine's coldstart status stream has its closed vocabulary pinned by hash (`coldstartStatus.ts`). `survey` is a fifth task kind a runner runs only with `survey_v1`; a `usage_tick` engine event carries raw token counts for one window, and the cloud prices it; and an optional `host_load` block on a claim carries free memory, free disk and the number of setups running, for routing and display only.
