## The two planes

The product lives in two repositories that hold the same product tree:

- The **code plane** is this public repository. All product code, pull requests, reviews, gate labels and CI live here.
- The **discussion plane** is a private repository. It holds planning and the team's own tooling, plus a small overlay of paths that never leave it. Its product tree is a copy of this one's `main`, kept in step by a sync after each merge here.

A product change is therefore one pull request on the code plane. A change that touches only overlay paths is a pull request on the private plane. The `pr-gates` job in `.github/workflows/ci.yml` runs only on public pull requests: it checks what the pull request body may cite and that the diff adds no overlay path. On the private repository, a pull request that changes only overlay paths skips the product suite and runs a smaller check instead; its jobs still finish `success` under their real names, because the merge gate refuses a required check that concluded `skipped`. A merge-queue run does the same when its tree is byte-identical to a pull request head that already carries the cloud's `fx-gate1` success: the `Same tree` step (`scripts/ci/same-tree.mjs`) proves that, and anything it cannot prove, or a queue group of several pull requests, runs the full suite (#923). A dormant `Rollup` step (`scripts/ci/rollup-position.mjs`, active only while the repository variable `ROLLUP_ENABLED` is `true`) lets a queue entry that has another entry on top of it wait rather than run the suites, and ends it as a success only once its own pull request is merged (#939).

## Request flow

For a request that reaches a tenant table:

1. A browser request hits `apps/web`. `apps/web/middleware.ts` runs an ordered list of steps before any route handler sees the request: it classifies CSRF risk from which credentials are present (`csrfStep`, in `apps/web/lib/shell/csrf.ts` — a cookie-only mutation is rejected unless `Sec-Fetch-Site: same-origin` or a matching `Origin` is present), verifies the session cookie (`@fx/core`'s `verifySession`) and exposes the decoded identity to the route as request headers, and rewrites shell session paths.
2. A route handler under `apps/web/app/api/**` calls into a package. The `/api/v1/*` routes all go through one dispatcher in `@fx/api` (a few route files, such as the assistant's, only raise the function duration); `@fx/core` does auth, session and work-item reads, `@fx/billing` the Stripe webhook, `@fx/db` tenant-scoped reads and writes.
3. Any tenant-scoped query goes through `packages/db/src/withTenant`, which opens a transaction and runs `SET LOCAL app.account_id` (and, where a caller passes one, `app.user_id` and `app.token_id` for a request authenticated by an API token rather than a session cookie) via a parameterized `set_config` call, then resets all three on the way out — never a plain `SET`, so a value can't leak onto a connection the pool hands out next.
4. Postgres evaluates each tenant table's row-level-security policy against that session-local `app.account_id`. `packages/db/migrations/0001_core.sql` defines these policies and enables `FORCE ROW LEVEL SECURITY` on every tenant table, so even the migration owner role can't bypass them. Newer tables follow the same pattern; where a write must be more than a tenant member may do, it goes through a `SECURITY DEFINER` function instead of a table grant (see [the data model](data-model.md#rls-conventions)).

`middleware.ts` runs on the Edge runtime, which has no Postgres connection, so its session check is a cryptographic/expiry check only — it can't see a revoked ("sign out everywhere") session. A Node-runtime route handler that needs revocation-aware identity goes through `apps/web/lib/shell/session-guard.ts`'s `resolveActiveSession` instead, which does reach the database.

## Pipeline

A work item moves through the stages in `packages/core/src/work-items/stages.ts`: `triaged`, `discussing`, `spec_ready`, `in_progress`, `pr_opened`, `changes_requested`, `review_passed`, `needs_human`, then one of the terminal stages `merged`, `closed_unmerged` or `closed`. The driver is deterministic code: a workflow in `apps/web/workflows/` advances an item and `packages/pipeline` holds the steps. No model decides whether an item moves on.

1. **Build.** At `spec_ready` the executor role runs (`packages/pipeline/src/build/stageMachine.ts`). A Spec that plans several pull requests becomes child items, each built on its own branch and stacked on its one open dependency. On a repository whose code lives on both planes, the build publishes a public pull request and keeps the private one as a paired copy.
2. **Review.** At `pr_opened` the required reviewers run for the item's tier (`requiredReviewers.ts`). Their verdicts come back as envelopes (below) and are recorded as labels and driver events. A failing verdict starts a fix round, bounded by the repository's settings.
3. **CI wait.** The review round waits for the pull request's CI on the exact head it reviewed (`packages/pipeline/src/review/ciWait.ts`) and says why it is still waiting. On a repository listed in `FX_GATE1_ATTEST_REPOS` the cloud also posts the `fx-gate1` status itself, see the next section.
4. **Merge gate.** `runMergeGate` (`packages/pipeline/src/build/mergeGate.ts`, `review/mergeGateRun.ts`) is the only place the product merges; a repo-wide test (`packages/pipeline/test/build/mergeCallSites.test.ts`) fails if any other file can call the merge. It returns either a merge or a list of fixed stop reasons. It checks the reviewers' verdicts on the current head, CI, mergeability, whether the pull request's author is one the platform merges for, ordered files (so a numbered file can't merge out of order), and the repository's merge dial. A merge by policy leaves a receipt. Two details: green CI on the head covers an acceptance tester whose latest run succeeded with the verdict `unverifiable`, provided the repository has CI of its own and not only the cloud's review status (#909); and a repository whose own CI is still running does not also get `repo_ci_missing`, which only a person could fix (#833). Every reader of check runs treats a run that has both a conclusion and a completion time as finished, whatever its `status` still says (`packages/pipeline/src/build/checkRunSettle.ts`, #821). The gate's recorded answer after a go order is keyed per merge order, not per head, so a second order on the same head leaves a fact of its own (`packages/pipeline/src/review/mergeGateRun.ts`, #979).
5. **Merge queue.** Where GitHub's merge queue is on, the gate puts the pull request in the queue instead of merging directly. `packages/pipeline/src/mergeQueue/` keeps one row per entry (`merge_queue_entries`), holds at most one merge in flight per repository through a database-enforced slot with a lease (300 s, renewed by every step), refreshes a head that fell behind, waits for CI, and starts a conflict, renumber or delta-review round (an agent run) when needed, releasing the slot while that run works. A per-repository lease (`mergeLease.ts`, `repo_merge_leases`) keeps a direct merge and the queue's slot from running at once on one repository. When the cloud's own gate enqueues a pull request it may ask GitHub for the front of the queue (`packages/pipeline/src/review/queueJump.ts`, #944): only in a repository listed in `FX_GATE1_ATTEST_REPOS`, only while `FX_QUEUE_JUMP` is unset, empty or `on` (any other value, `off` included, turns the jump off), and at most once per repository in `FX_QUEUE_JUMP_MIN_MINUTES` (default 50) because a jump makes GitHub rebuild the entries already running. A jump GitHub refuses is retried once as a plain enqueue (`packages/pipeline/src/build/githubMergePort.ts`), so the pull request only loses its place. A team's own pull request never passes through this code.
6. **Post-merge verify.** Off by default for a repository (`packages/core/src/verify/settings.ts`: `enabled` is false until an owner or admin turns it on). Where it is on, a third pass of the claim verifier's 15-minute tick (`packages/worker/src/verifyStage.ts`) picks up items that the product merged after verification was switched on, within a 24-hour lookback, and opens a verify row for each (`packages/core/src/verify/rows.ts`). The row moves one way: `pending`, `deploying`, `running`, then `verified`, `failed` or `unverified`; the one exception is a running check parked for a new sign-in (below). For one repository it works one row at a time:
   - It places one deploy order for the merge commit, which a runner on the repository's own machine claims, then polls the app's `/api/health` for up to 15 minutes until the reported commit is the merge commit or a genuine sync commit that descends from it. A failed deploy ends the row `unverified: deploy_failed`; an app that never answers ends it `deployment_unreachable`, one that answers with another commit `commit_not_deployed`.
   - Once the commit qualifies (`packages/worker/src/verifyRun.ts`), it starts one `deploy-verifier` job on a runner, with the checkout pinned to the merge commit. A repository that does not run work on a runner ends `unverified: no_browser`. A repository whose daily verify budget is used up holds the row at `deploying` until the next tick.
   - Before a job starts, the stage reads what the account's runners last said about their saved verify sign-in (`packages/core/src/verify/signIn.ts`, #947). When every runner that has said anything reports it `expired` or `missing`, the row is held with the reason `needs_sign_in` instead of starting, since the job would only come back without an account. A runner that never reported (an older build) does not hold a row. If the app turns out not to know the sign-in while the check runs, the row goes back from `running` to `pending` with the same hold and starts again once a runner reports a good sign-in newer than the hold. A row waits at most 24 hours and is parked at most three times before it ends `unverified: sign_in_expired` (`packages/core/src/verify/rows.ts`, `packages/worker/src/verifyRun.ts`).
   - A criterion may carry a `[start: <app id>]` marker naming the first-party app a browser journey opens first. Only ids on a closed list (`packages/core/src/verify/startApps.ts`, #957) are kept, so spec text cannot name a page or a URL. The list now includes the Team app (`team`, #999). The Runners app is now called Machines (#1180); its id is still `runners`.
   - The tester answers with a JSON envelope of journeys (the Spec's criteria plus the repository's standing journeys), each `pass`, `fail` or `blocked`. The pipeline parses it strictly and decides; a `pass` without a step and an undo check is refused as a hollow pass and the row ends `unverified`, and so is one without a reload, unless the journey is marked view only (a filter, sort or reading, which resets on reload by design) (`isEvidencedPass` in `packages/core/src/verify/rows.ts`, #982).
   - A `failed` row files one bug item, keyed on the row and its first failing journey (`packages/core/src/verify/bugItem.ts`). A row that could not check anything files none. The streak of consecutive `verified` rows is derived from the finished rows: a pass counts, a `failed` or `unverified` row resets it.

### The cloud's own `fx-gate1`

`fx-gate1` is a commit status on a public pull request's head that the repository's ruleset requires. For a cloud item:

- The cloud posts it itself, from a green full-scope run of the public CI on that exact head (`gate1Attest.ts`). It reads only GitHub's own records: which app ran each of the five CI contexts (GitHub Actions only), their start times against the time of the last `ci:full` label event, and the changed paths. A change that touches CI files is refused.
- It posts it for the head of the pull request and also for each merge-queue entry commit (`gate1QueueEntry.ts`): the entry gets success only when its five contexts are green on the entry commit and every pull request ahead of it in the group already carries the cloud's own `fx-gate1` success. When a pull request leaves the queue, merged or dequeued, the entries still queued on that base branch are listed again and re-checked (`listQueueEntryCandidates`, #917).
- An item that was already in flight when the setting went on is attested at the merge gate and at the queue entry too, not only in the review round.
- The merge gate counts `fx-gate1` only when the cloud's App posted it (`gate1Creator.ts` reads who posted it). A status from a person, a token or another app is not counted, and the gate stops with `gate1_status_foreign`.

It is off unless the repository is listed in `FX_GATE1_ATTEST_REPOS` (see [operations](operations.md#settings-an-operator-sets)).

### Where an agent runs

A repository has an execution mode (`repos.execution_mode`, `packages/runner-cloud/src/executionMode.ts`):

- `sandbox`: the cloud runs the agent in a hosted Vercel sandbox (`packages/runner/src/vercelSandboxPort.ts`). Every sandbox is created from one pinned image and with its network policy; a create without a policy is refused before any SDK call.
- `runner_local`: the agent runs on the customer's machine under `packages/fx-runner`. The cloud never receives the repository's contents: every GitHub call the cloud makes about such a repository passes an allowlist of a few fixed calls (`packages/runner-cloud/src/localOnlyGithub.ts`), and the runner checks content and merges the public pull request itself after the cloud's go. The one pull request the cloud builds itself for such a repository is the one that takes the engine's files out again (#1193): through the GitHub App it creates one branch (`fx/engine-remove-<version>`), one commit of deletions and one pull request, reading only paths, modes and blob ids. It deletes a file only when the merged install pull request added it and nobody has changed it since; every other file stays and is listed in the pull request's body (`packages/runner-cloud/src/engineRemovalPr.ts`, a separate narrowed allowlist in `localOnlyGithub.ts`).
- `runner_verified`: the agent runs on the customer's machine and the cloud verifies the result.

On the machine the job runs in an OS sandbox today (Linux; macOS and WSL2 are previews, and WSL2 starts only when its live safety probes pass). A second engine, Firecracker microVMs, is wired into `run` but a whole job through it in a real VM is not yet proven. Its pieces:

- **The helper** (`packages/fx-runner/vmhelper/`, Go): a root service that starts each VM through the pinned jailer, in its own cgroup and under its own uid. It does only the privileged work.
- **sandboxd** (`packages/fx-runner/src/vm/sandboxd/`): an unprivileged daemon that refuses to run as root. It names sandboxes, runs commands in them, applies the network policy and asks the helper for anything privileged. `live.ts` puts the daemon, the SDK adapter and the microVM sandbox port together, and returns nothing unless every part is there.
- **Boot facts** (`packages/fx-runner/src/vm/bootFacts.ts`): what a VM may boot from. They come from the template the machine installed and the signed release listing, and nothing else; a missing, expired or unlisted image refuses with a closed code and no VM starts.
- **The workspace crossing** (`packages/fx-runner/src/vm/workspace/crossing.ts`): the repository is built on the host from the runner's own mirror and sent into the guest before the agent starts, and what the run committed comes back as a bundle for the host to check and apply. A resumed session is refused (`workspace_missing`) unless the guest's copy still matches the commit that was sent.
- **The fresh-VM check** (`packages/fx-runner/src/vm/workspace/guestCheck.ts`): the approved check runs in a new VM the agent never had, and the host reads the exit code and decides. The agent has sudo in its own VM, so its verdict would not be trusted.

`run` composes this stack (`packages/fx-runner/src/vm/sandboxd/live.ts`, `packages/fx-runner/src/commands/run.ts`), and the entry point (`packages/fx-runner/bin/fx-runner.mjs`, through `packages/fx-runner/src/vm/liveParts.ts`) supplies every part: the boot facts over the signed release listing and the installed manifest, the template, the guest agent runtime and the model token's reader. `run` wires the job handler's VM side over it (`packages/fx-runner/src/daemon/vmJobDeps.ts`): the working-copy crossing, the archive, the bundle apply, the fresh-VM check and the lifecycle that makes, stops and deletes each job's VMs. A build that lacks any one part stays unwired: a runner set to the `microvm` engine claims nothing (`microvm_build_unwired`) and never falls back to the OS sandbox. Each VM is bound with its run's own usage and relay sinks (the ones the OS-sandbox path passes its engine), so a guest's usage events and near-limit warnings reach the usage gate and the cloud's priced usage; the claim loop stops at the VM cap on the lifecycle's own registry; and before the first claim `run` ends the VMs the helper still holds from an earlier process, holding claiming while any cannot be ended (`vm_reap_pending`). A runner on an API key claims nothing in this mode (`microvm_api_key_unsupported`). A real-VM run of a whole job through `run` is not yet proven (the next row), and the startup reap covers only what the helper lists at start.

One orchestrator, `runVmJob` (`packages/fx-runner/src/vm/jobLifecycle.ts`), owns every VM of a job: it makes the agent's VM and, later, a fresh one for the check, enforces the VM cap, and deletes both on every way out. The agent step is the ordinary job code over the VM it made (the production VM factory is `packages/fx-runner/src/vm/sandboxd/vmPort.ts`), and the guest runs the agent CLI itself (`packages/fx-runner/src/vm/sandboxd/guestRuntime.ts`). The job's model token is not in the VM's environment when it boots: it goes over vsock into a memory-only directory after the VM is up and reaches exactly one program, the agent CLI, started as the ordinary user in its own cgroup (`packages/fx-runner/src/vm/sandboxd/jobToken.ts`). Before the VM is stopped, snapshotted or its commits are read out, the runner removes the file, kills every process in the token's cgroups and waits for the guest to confirm that none is left; a wipe the guest does not confirm ends the job `vm_teardown_incomplete` and the VM is deleted instead of snapshotted. The other closed job-end codes are `vm_admission_refused`, `vm_boot_failed`, `vm_egress_unavailable`, `vm_token_delivery_failed` and `vm_workspace_failed`, none with free text. The runner reports its sandboxes and host limits on its claim, and an owner or admin can queue a signed stop, delete or reap command for them: the cloud signs it in the worker's composition root and hands it over on the claim reply (`packages/runner-cloud/src/sandboxCommands.ts`, `packages/worker/src/compositionRoot.ts`, migrations 1040 and 1041). A runner set to `microvm` that cannot start a VM names one of four reasons (no KVM, helper missing, not ready or out of date; migration 1044). Both are for routing and display; no security decision reads the runner's list.

Reviews follow the same split. A review run on a hosted sandbox counts at the merge gate; a run on the customer's runner counts only when local review is on for the repository and the runner is trusted for that role (`runner_not_trusted_*` stop reasons otherwise).

### The engine bridge

A person can run the autonomous team (the engine) on their own machine and watch or operate it from the workspace. This is a separate path from the pipeline above, off by default: an owner or admin turns on a watch switch and, separately, an operate switch for the account, and ticks the repositories (`engine_bridge_settings`, `engine_bridge_repos`, migration `packages/db/migrations/1027_engine_bridge.sql`, #1001). Everything the cloud shows is computed from closed facts the engine reports (ids, enums, counts, timestamps), never from prose, and none of it feeds a spend cap.

- **Setting it up on the machine.** The person runs `fx-runner engine-bridge enable --repo <owner/name>` there. Without `--repo-root` the runner looks for the one engine checkout of that repo under the usual folders in the home directory, the current directory and any roots in `FX_RUNNER_SEARCH_ROOTS` (`packages/fx-runner/bin/fx-runner.mjs` passes both in, `packages/fx-runner/src/engineBridge/discover.ts` does the scan), and takes the engine's state directory from that checkout's `.autonomous-team/project.json`. It refuses, and changes nothing, when it finds none, several, or one in a scan that hit its limit (#1100, #1107). The workspace's Team window shows this command with the repo name filled in and nothing left to edit (`apps/workspace/apps/team/team-runners.js`, #1105); it adds `--repo-root` only when a runner has reported a folder, and none does yet.
- **Connect.** A person can also do that setup from the workspace. An owner or admin presses Connect and the cloud sends a `bridge_enable` command to a runner the account owns that is paired with the repo, not to an engine session, optionally with a folder. The runner finds the checkout as above, answers with the last two parts of the folder it chose or up to ten folders to pick from (a search cut short says so), and reports which repos it bridges. "Connected" is read from that report, never stamped by the cloud, and it lapses after 24 hours without a fresh one. Disconnect sends `bridge_disable`. At most five bridge commands per account in ten minutes (`packages/db/src/engineBridgeConnect.ts`, migrations 1042 and 1046). The runner reads the engine's version from the engine's own manifest, or from the install record in a project that has the engine installed (`packages/fx-runner/src/engineBridge/engineVersion.ts`, #1143).
- **Watch mode.** While nobody has the Team app open on a repo, the runner keeps the heavy events (the on-demand kinds, and the engine's and host's heartbeats) on the machine and sends only a `slim_status` event, one age in seconds per source (bridge, host, engine). Opening the page sends a signed `watch` command that runs at most ten minutes ahead; the held events then arrive in a separate detail session of their own, so the engine session's strict order is unchanged. A hole in an engine session that is only held-back events is flagged `held` and left out of "missing events". A runner takes this only if its hello declared `watch_mode_v1` (migration 1043). The page asks for the watch through `POST /api/v1/engine/repos/{id}/watch` (`packages/api/src/routes/engine-watch.ts`, #1172), which any member of the account may call: it takes a lease for the repo, the person and the browser (`engine_watch_leases`, migration 1049) and issues the `watch` command only when none already covers the view. How many people may watch one engine at once (per repo and per account), how long a view lasts and how long it may sit idle come from the plan data (`watch` on each plan and on the runner plan); a missing figure answers 503, never an unlimited view, and a full plan answers 429 `watch_limit`. The page's event stream renews the lease while it stays open and removes it when it closes; `DELETE` on the same path ends the view, and a closed browser frees its slot after 90 seconds.
- **Public repositories.** A repository whose visibility GitHub answers, public or private, can be watched; one GitHub does not answer is refused as `repo_visibility_unknown`, and the answer is asked afresh each time, never stored. Turning operate on for a public repository is refused as `operate_public_pending` until the rule for work from strangers exists. Project confirmation reads the visibility before its transaction opens (`packages/api/src/routes/engine.ts`, `packages/runner-cloud/src/projectConfirm.ts`, #1220).
- **Machine jobs.** The cloud can ask a person's own machine to set a project up. A job is a row signed when it is issued (`signMachineJob`, handed to the worker beside the engine command signer in `packages/worker/src/compositionRoot.ts`); a claim reply tells a runner a job waits, `POST /api/runner/machine-job/claim` hands it over once, and the runner reports each step to `POST /api/runner/setup/{setup_id}/progress` (`packages/runner-cloud/src/machineJob.ts`, #1179). The runner fetches the plan from `GET /api/runner/setup/{setup_id}/plan` and runs it in a microVM or, on a standard machine, in the OS sandbox (`packages/fx-runner/src/setup/hostGuest.ts`, #1184, #1225); `POST /api/v1/setups/{id}/install/retry` issues the next attempt of a failed install (#1183). The same dispatcher also takes the three engine-session kinds (`engine_session_start`, `engine_session_stop`, `engine_session_delete`): `run` builds their handlers over the microVM stack only when that stack and the runner's uid are present, and a session job reports on the machine-job route by its own job id instead of through a setup (`packages/fx-runner/src/commands/run.ts`, `packages/fx-runner/src/daemon/machineJobs.ts`, `packages/fx-runner/src/engineSession/lifecycle.ts`, #1222). The dispatcher also takes the kind `engine_update`, which brings an installed project's engine files to a newer release on its own branch: `run` builds its handler (`packages/fx-runner/src/setup/engineUpdate.ts`) over the same two guests, it reports on the same progress route, and the route reaches the update's own definers by the job's kind (`packages/runner-cloud/src/engineUpdateDefiners.ts`, `packages/runner-cloud/src/machineJob.ts`); `POST /api/v1/engine/repos/{id}/update` issues it (#1284). A setup job's last runner step is the push: the runner asks `POST /api/runner/setup/{setup_id}/push-token` for a one-repository credential and pushes the install commit itself (#1228). The cloud then opens the install pull request, or in direct mode finishes, from the level-triggered reconcile job `setup_install_pr` (`packages/runner-cloud/src/setupInstallPr.ts`, #1229). The pull request is opened as a draft, held to the path policy, labelled, and only then marked ready; a webhook delivery that merges it moves the setup to `finish`, and one that closes it unmerged fails the setup `pr_closed` (#1234). The merge is a person's click (`POST /api/v1/setups/{id}/install/merge`, after reading what the pull request holds from `GET /api/v1/setups/{id}/install/summary`, #1263), and a setup at `finish` is then finished by the reconcile job `setup_finish`, which makes the plan's first Discussions and the team-log issue (`packages/runner-cloud/src/setupFinish.ts`, #1258); the job `engine_session_starts` then signs the project's first engine session when the repository is placed, operated and covered by the plan (`packages/runner-cloud/src/engineSystemStarts.ts`, #1284). Before the plan there is a survey of an existing project: the cloud starts a read-only run of the `project-surveyor` role on the placed machine and ends it itself if it never answers (#1242, #1245, #1250, see [the runner page](packages/runner.md#the-project-survey-run-1242-1245-1250)). A public repository's survey never starts by itself: the confirm reply says `public_survey_consent_required` instead of starting one, and the person's consent to `POST /api/v1/setups/{id}/survey/start` starts it (`packages/runner-cloud/src/projectConfirm.ts`, #1284). The cloud also stops an engine session on its own when the operate switch goes off, a repository is un-ticked or the engine plan ends (the reconcile job `engine_session_stops`, #1243), and removing a project queues the machine's cleanup, which the machine's own claim turns into stop and delete jobs (#1252). See [the runner page](packages/runner.md#a-project-setup-job-1181-1184-1225).
- **Machine facts.** The cloud can store a runner's free memory, free disk and number of setups running (`runner_facts`), and whether it holds model credentials (`runners.model_auth_present`). The runner sends the load on a claim at protocol 22 and later, at most once a minute, whatever capabilities its build advertises. An idle runner claims only when woken (or once per safety slot), so a confirm that finds the load missing or older than three report intervals answers 409 `machine_not_eligible` with the closed reason beside the error (`load_unknown`, and the others: `not_live`, `paused`, `draining`, `claude_not_ready`, `low_memory`, `low_disk`, `server_deleting`), marks runner work for the account (the push the wake store already carries; no poll) and the Onboarding picker asks again a few seconds later, saying "Checking the machine…". The runner's hello also says whether the machine has a usable KVM device (`runners.kvm`, `present` or `absent`, empty for a runner that did not say; the capability `kvm_fact_v1`, migration 1047). No security or routing decision reads these facts. The Onboarding app's engine track words its machine step from them, and the placement library reads the load and the model-credentials flag to decide which machine may take a project: a machine is eligible only when it is live, has no project yet, is not paused or draining, holds model credentials and has a recent load reading with enough free memory and disk, and a fact the machine never sent counts as unknown, never as enough. `placeProject`, `autoPlaceProject` and `moveProject` (`packages/runner-cloud/src/placement.ts`) write the `project_placements` table, one project per machine. `POST /api/runners/repos/{id}/place` confirms a project in one transaction that writes the setup row, the runner mode, the placement, the machine's repository list and an audit row together, and `/move` moves one (`packages/runner-cloud/src/projectConfirm.ts`, #1180, #1220). A placement change takes the machine's lock, and a deadlock between two of them answers `placement_busy` for the caller to retry (#1223) (`packages/runner-cloud/src/machineFacts.ts`, migrations 1035, 1045 and 1047).
- **Up.** The runner (`packages/fx-runner/src/engineBridge/`) starts the bridge from `run` only when its entry point (`packages/fx-runner/bin/fx-runner.mjs`) passes in the halt path and the dial ceiling keeper built by `createEngineBridgePorts` (`packages/fx-runner/src/engineBridge/ports.ts`, `packages/fx-runner/src/commands/run.ts`, #1022). It tails the engine's events file and, beside it, the engine host's own events file (`engine-host-events.jsonl`, written by `packages/fx-runner/src/engineHost/hostFeeds.ts`, #1044). Each file has a cursor of its own and neither can put events into the other's session (`createBridgeTails` in `packages/fx-runner/src/engineBridge/daemon.ts`); their events are merged by time into one stream, one request per engine instance. It posts batches, signed with the runner's own key, to `/api/runner/engine/events`. A batch of ordinary events is held up to 60 seconds so several go out together, while an ask, an ask clearing and the halt answer go at once, and a batch of nothing but "alive" events waits until the runner's status is due, which is when the cloud has heard nothing from it for 5 minutes (`UNWATCHED_COALESCE_MS`, `URGENT_KINDS` and `HEARTBEAT_MS` in `packages/fx-runner/src/engineBridge/loop.ts`, #1036). While the account's switch for the repo is off, the loop tries again every 5 minutes, and a change in the runner's wake epoch ends that wait early (#1050). After each pull the cloud answered, the bridge daemon also writes the small local file the engine host reads to know the bridge and operate are on, and removes it when the repo's bridge stops (`packages/fx-runner/src/engineBridge/daemon.ts`, #1047). The cloud stores them through a database function that checks the switches, the repo, the runner and the strict sequence order, and writes the read model in the same transaction (agents, merge lanes, gate receipts, asks, usage; `packages/db/migrations/1027_engine_bridge.sql`). A repo's plan and roadmap arrive as chunks of one snapshot (`packages/db/migrations/1032_engine_plan.sql`, #1004).
- **Down.** An owner or admin sends one of seven commands (`start_day`, `pause_loop`, `resume_loop`, `answer_ask`, `set_dial`, `request_spawn`, `stop_agent`) with `POST /api/v1/engine/repos/{id}/commands` (`packages/api/src/routes/engine-commands.ts`, session only, at most 20 waiting commands per runner and repo, `MAX_PENDING_PER_TARGET` in `packages/db/src/engineCommands.ts`). The cloud signs it with the job-signing key (`engineCommandSigner` in `packages/worker/src/compositionRoot.ts`), and the runner pulls it from `/api/runner/engine/commands/pull` (at start, when its wake check sees a change, and as a safety net every 10 minutes, or every 20 seconds until a wake answer has been seen; `packages/fx-runner/src/engineBridge/commands.ts`), checks it, hands it to the engine and acknowledges the outcome (#998, migration `packages/db/migrations/1029_engine_commands.sql`). A command lives at most ten minutes. Changing the switches, the ticked repositories or a repository's execution mode marks the account's runner work, so the runner hears of it through the wake path rather than at its next pull (`packages/api/src/routes/engine.ts`, `packages/runner-cloud/src/executionMode.ts`, #1036).
- **Decisions.** Before the engine spawns an agent, merges a pull request or marks a Spec ready, it asks `/api/runner/engine/decide` through a local socket on the runner. The cloud answers from the repo's dial (`engine_spawn`, `engine_merge`, `engine_spec_ready` in `packages/decisions`), and a decision that needs a person shows up as an ask they answer with `POST /api/v1/engine/decisions/{id}/answer`. The answer is stored whatever the operate switch, the engine connection or a halt is doing, sends the engine no command, and is read back by the engine's next ask with the same request key (approve is act, decline stays ask) (#993, #1028, migration `packages/db/migrations/1030_engine_decisions.sql`). `/api/runner/engine/dials` hands the runner the resulting ceilings, which it writes as a short-lived file the engine reads (#1002).
- **Halt.** `POST /api/v1/engine/repos/{id}/halt` sets a per-repo marker (`engine_repo_controls`, migration `packages/db/migrations/1031_engine_halt.sql`, #992) until a person clears it with `halt/clear`. While it is set, decide answers `ask` with `halted: true` and writes no receipt (`packages/runner-cloud/src/engineHaltReplies.ts`), and the command insert trigger refuses the start-like kinds (`start_day`, `resume_loop`, `request_spawn`, `set_dial`) with HX409. A halt bumps an epoch the runner reads and kills the engine on; a clear never lowers it. A command inserted from a person's session is stamped with exactly the current epoch by the insert trigger, whatever value the route passed (`packages/db/migrations/1034_engine_halt_stamp_exact.sql`, `packages/api/src/routes/engine-commands.ts`, #1024). Setting and clearing run through two `SECURITY DEFINER` functions that check the caller is an owner or admin session.
- **Read.** The workspace's Team app and the engine items in Needs you read `/api/v1/engine/...` (`packages/api/src/routes/engine.ts`, #1003) and the live `engine.changed` event. The settings read also names, per repository, the runner whose bridge last reported for it (`bridged_runner_id`), so the Team app can say which runner its watch switch means (#1080). The notice carries the repo and session ids, the last sequence number and `panels`, the names of the panels the stored batch touched, taken from the closed set agents, lanes, gates, asks, log, plan, stats, usage and status, so a reader can re-read only those (the Team app reads only the parts a notice names, each at most once in 10 seconds, #1058); an event kind the map does not know names every panel. The notice wakes an account's open streams at once through the same nudge path as a revoked session (`packages/db/migrations/1039_engine_notice_panels.sql`, `packages/api/src/sse/nudge.ts`, #1056), instead of waiting for the poller's next idle tick. The repos list carries each repo's real halt state (`halted`, `halted_at`, `halted_by`, `halt_epoch`, `halt_pending`; #1027, #1046). `halted_by` is the id and display name of the member who set the halt, and is null when nothing is halted, when the halt predates the column, or when that person is no longer a member of the repo's account (`packages/core/src/engine/panels.ts`; the Team app shows it as "Halted by <name> at <time>"), and each panel read carries its own `as_of`, the time its newest event reached the cloud (the repo-wide stamp when it has had none), and the freshness block adds `held_events` and `oldest_seq` for the lines the runner keeps back until someone watches (`packages/api/src/routes/engine.ts`, #1185, #1189); a runner counts as heard when its wake check was seen more recently than its last upload, but only while its last upload is at most 7 minutes old, so a runner whose bridge has died is not kept live by its daemon (`WAKE_STAMP_MAX_DB_AGE_S` in `packages/core/src/engine/panels.ts`, read through `apps/web/app/api/v1/[...path]/route.ts`, #1036), and the asks list returns the team-log asks and the decision asks together, a decision ask carrying a `decision_id` and `decision_type` and clearing when answered (#1028). See [the workspace app](apps/workspace.md).

### The review sandbox image

Hosted agents and their checks run in the image built from `infra/sandbox-image/`. Besides the pinned agent CLIs it carries the Postgres 18 server binaries (`initdb`, `pg_ctl`, `postgres`, so the Postgres-backed test projects can start a throwaway cluster) and a Playwright Chromium, because a running sandbox has no network to download either. ### Verdict envelopes

Every reviewer ends its final message with an `AGENT_OUTPUT` block holding a JSON verdict. `packages/runner-protocol/src/envelope.ts` parses it, and the rules matter because text a reviewer reads can quote a planted block:

- The last block wins. A malformed last block gives no verdict; an earlier block is never a fallback.
- A block's body may not contain another opening marker, and input over 256 KB is refused.
- On a hosted sandbox, when the final turn of a run has no envelope because the agent spoke again after giving its verdict (a background task finished), the envelope of the last main-thread message that carried a marker is used (`packages/runner/src/vercelSandboxPort.ts`), but only if that message ends with the block (`endsWithEnvelopeBlock` in `packages/runner-protocol/src/envelope.ts`), so a block quoted mid-message never counts (#834). Subagent lines never feed it, a checkpoint verdict never counts, and a later marker that does not parse clears it.
- The sandbox port reads the agent's output from a record file written by a recorder script that wraps the CLI, read back in slices and checked against the command's own echo at exit (`packages/runner/src/recordParser.ts`, #840, #844, #852).

## The assistant

`POST /api/v1/assistant/messages` (`packages/api/src/routes/assistant.ts`) is a per-repository chat for a person. It answers from the person's own model key and can only read or propose.

- **Session only.** No API token of any kind is accepted.
- **Closed tool registry.** The model sees seven tools (`packages/core/src/assistant/tools.ts`): the reads `get_item`, `get_spec`, `get_run_activity`, `get_verdicts`, `get_plan` and `list_corrections`, and the one write, `draft_correction`, which for a `spec_amend` may also name up to 10 plain file paths in `add_files` to add to the Spec's file list (#978). A tool name outside the list is dropped and never run. Tools run in-process under the caller's own principal, and an item of another repository answers "not found".
- **Proposal only.** `draft_correction` writes a `proposed` correction with origin `agent`; a person still has to accept it. The assistant can't accept, reject, merge, cancel or change anything.
- **RLS.** The tools read through the same tenant-scoped reads as the rest of the app. A conversation row is visible to its creator and to an owner or admin of the account, and only while the account is active.
- **Cost cap per conversation.** The cap is fixed when the conversation starts (`assistant_conversations.cap_micro_usd`). Each model call, a tool round included, is admitted at its worst case first and settled at its real cost; a call that would pass the cap is refused with the `budget_reached` state. A model the platform can't price gives `unpriced` and makes no call.
- **No message storage.** The client sends the turns so far each time. The tables hold only money and ids; no message text, correction text or repository text lands in them.
- **Streaming.** With `Accept: text/event-stream` the answer arrives as `conversation`, `text`, `tool` and `done` events; closing the request stops the turn and settles what was used.

The same file issues the assistant's delegation token (one hour at most, one repository, scopes `read` and `corrections:write`) and the device-link flow that hands it to a customer's runner.
